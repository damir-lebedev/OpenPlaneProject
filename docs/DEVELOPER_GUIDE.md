# DEVELOPER_GUIDE.md — Руководство разработчика OpenPlaneProject

Техническая карта прошивки: какой файл за что отвечает, как текут данные от
приёмника и датчиков до сервоприводов, какие соглашения о знаках держат всю
цепочку вместе, как устроен веб-API и как расширять проект. Рассчитан на
разработчика, который пишет на C++ и хочет быстро сориентироваться в этом
репозитории (ветка `main`), а не на изучение основ языка или PlatformIO.

Обзор проекта и статус прототипа — в [`../README.md`](../README.md), что куда
подключать и как летать — в [`PILOT_GUIDE.md`](PILOT_GUIDE.md), планы — в
[`ROADMAP.md`](ROADMAP.md). Здесь — только код.

> Проект в активной разработке. Стенд на ESP32-S3 собран и проверен со всеми
> датчиками, но **автопилот ещё не испытан в полёте** — это отмечено там, где
> касается конкретного модуля. Сомневаетесь, что делает код, — перечитайте
> исходник, а не документ.

## Архитектура слоёв

Классы почти целиком живут в заголовках (`include/*.h`). `src/main.cpp` —
единственная точка сборки (composition root): создаёт все объекты, связывает
их и крутит `setup()`/`loop()`. Зависимости однонаправленные — нижний слой
ничего не знает о верхнем.

```
┌───────────────────────────────────────────────────────────────────────┐
│ APPLICATION  src/main.cpp                                             │
│   composition root, консоль отладки, цикл с фиксированным периодом    │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ владеет и вызывает
                               ▼
┌───────────────────────────────────────────────────────────────────────┐
│ COORDINATION                                                          │
│   FlightController.h      — единственный оркестратор update()         │
│   AutopilotModeSelector.h — CH7 -> режим автопилота                   │
│   DebugLogger.h           — состояние в Serial                        │
│   WebDebugServer.h        — веб-дашборд (своя задача, ядро 0)         │
│   OledDisplay.h           — экран статуса (своя задача, ядро 0)       │
│   LoopStats.h             — частота и время цикла                     │
└───────┬───────────────────────┬───────────────────────┬───────────────┘
        │                       │                       │
        ▼                       ▼                       ▼
┌────────────────────┐  ┌──────────────────────┐  ┌──────────────────────┐
│ FLIGHT LOGIC        │  │ FLIGHT LOGIC          │  │ FLIGHT LOGIC          │
│ (ручное управление) │  │ (автопилот)           │  │ (общее)               │
│ ControlMixer.h      │  │ Autopilot.h           │  │ ArmingManager.h       │
│ ThrottleManager.h   │  │ (PID_Controller +     │  │ FlightOutputState.h   │
│                     │  │  4 режима)            │  │ (POD-контракт)        │
└─────────┬───────────┘  └──────────┬────────────┘  └──────────┬───────────┘
          │ RcChannelState          │ ImuSensor* / BarometerSensor* / ...
          ▼                         ▼                          │
┌────────────────────────────┐  ┌──────────────────────────────┴────────┐
│ RC                          │  │ SENSORS                               │
│ RcChannelState.h (снимок)   │  │ SensorInterface.h — абстракции        │
│ RcInput.h (clamp/centered)  │  │ MPU6050_Sensor (MPU6050/6500)         │
│ IBusReceiver.h (IUartPort → │  │ ICM42688_Sensor                       │
│   каналы + потеря связи)    │  │ BMP388_I2C / BMP388 (SPI) / BME280    │
│ Channels.h (имена каналов)  │  │ QMC5883P / QMC5883L, UbloxM10_Gps     │
│                             │  │ SensorSelection.h — какой чип выбран  │
└─────────────────────────────┘  └───────────────────────────────────────┘
          │                                       ▲
          ▼                                       │ II2CBus / ISpiBus / IUartPort
┌───────────────────────────────────────────────────────────────────────┐
│ OUTPUTS  FlightOutputs.h — порядок 5 выходов, пишет через IServoOutput │
└──────────────────────────────┬────────────────────────────────────────┘
                               ▼
┌───────────────────────────────────────────────────────────────────────┐
│ HAL — "МОЗГ"  include/hal/                                            │
│   IBoard / II2CBus / ISpiBus / IUartPort / IServoOutput — интерфейсы  │
│   hal/esp32/Esp32Board.h (+ Esp32I2CBus / Esp32SpiBus /               │
│     Esp32UartPort / Esp32ServoOutput) — обёртки над                   │
│     Wire / SPI / HardwareSerial / LEDC                                │
│   Config.h — выбор платы (BOARD_ESP32_*), пины, все настройки         │
└───────────────────────────────────────────────────────────────────────┘
```

Правила, которые держат архитектуру чистой:

- **HAL** — единственный слой, которому разрешено знать конкретный MCU
  (`Wire`, `SPI`, `HardwareSerial`, `ledc*`). Всё выше работает только с
  интерфейсами `IBoard`/`II2CBus`/`ISpiBus`/`IUartPort`/`IServoOutput`.
  Переход на другой MCU — это новая `hal/<mcu>/<Mcu>Board.h`, остальной код
  не меняется.
- **RC и Outputs** не знают про самолёт: только байты iBUS → каналы и
  значения PWM → выходы.
- **Sensors** не знают про автопилот: читают шину через интерфейсы HAL и
  отдают `ImuData`/`BarometerData`/`MagData`/`GpsData`. Какой чип
  скомпилирован — решает `sensors/SensorSelection.h`.
- **Flight logic** (`ControlMixer`, `ThrottleManager`, `ArmingManager`,
  `Autopilot`) — логика над данными, без UART, PWM и Wi-Fi.
- **Coordination** — единственный слой, который видит сразу несколько нижних
  и решает порядок операций.
- **Application** (`main.cpp`) — единственное место, где создаются
  `Esp32Board` и конкретные датчики (через `SelectedImu`/`SelectedBaro`/
  `SelectedMag`/`SelectedGps` и макросы `SELECTED_*_ARGS`), и где всё
  связывается руками, без DI-фреймворка.

## Задачи FreeRTOS и цикл управления

| Где | Что | Период |
|---|---|---|
| Ядро 1, `loop()` (Arduino loopTask) | `applyPendingCommands()` → `FlightController::update()` → `DebugLogger::update()` → консоль | `Config::LOOP_PERIOD_MS` = 2 мс (500 Гц), `vTaskDelayUntil` |
| Ядро 0, задача `web` | `WebServer::handleClient()` | каждые 2 мс |
| Ядро 0, задача `oled` | отрисовка SSD1306 по Wire1 | 200 мс |
| Ядро 0 | Wi-Fi стек ESP-IDF | — |

- Период цикла держится `vTaskDelayUntil`, а не `delay(2)` после работы —
  частота не зависит от того, сколько длился такт. После долгой блокировки
  (калибровка из консоли) отсчёт начинается заново, пропущенные такты
  пачкой не догоняются.
- На стенде (ESP32-S3, все датчики): 500 Гц, в среднем ~0.9 мс работы на
  такт, худший такт ~2.1 мс. Раз в 10 с это печатается строкой `SYS:`.
- **Разделение данных между задачами.** Веб и OLED только *читают*
  состояние (`FlightController`/`Autopilot`/`LoopStats`) — это отдельные
  16/32-битные поля, в худшем случае видны значения соседних тактов.
  *Команды* с дашборда (`setmode`/`setpid`) из веб-задачи напрямую не
  применяются: они кладутся в «почтовый ящик» под `portMUX` и забираются
  полётным циклом в `WebDebugServer::applyPendingCommands()`.
- `Serial` (UART0 → мост CH343 → разъём «COM») с буфером передачи 4 КБ:
  отладочный кадр (~600 символов) не блокирует цикл на время отправки.

## Соглашение о знаках: от IMU до сервопривода

Одна система знаков на всю цепочку — поэтому стик и автопилот гарантированно
двигают рули в одну сторону, а направление каждого сервопривода задаётся
ровно в одном месте.

**1. Оси датчика → оси самолёта.** Драйвер IMU поворачивает оси чипа по
`Config::IMU_ROTATION_CW_DEG` (плата лежит микросхемой вверх; значение — куда
смотрит ось X *чипа*, если нос — «12 часов»). Получаются оси самолёта:
X к носу, Y влево, Z вверх.

> На текущем GY-521 (клон с MPU6500) чип запаян повёрнутым на 90° относительно
> нарисованных стрелок: стрелка X на шелкографии = ось Y чипа. Поэтому
> `IMU_ROTATION_CW_DEG = 90`. Проверка после любой перестановки: нос вверх →
> P растёт в плюс, правое крыло вниз → R в плюс.

**2. Углы и скорости (`ImuData`) — авиационные знаки:**

| Величина | «+» означает |
|---|---|
| `roll`, `gyroX` | правое крыло вниз |
| `pitch`, `gyroY` | нос вверх |
| `yaw`, `gyroZ` | нос вправо (по часовой сверху) |

**3. Команда (`ControlCommand`, мкс отклонения, ±500 = полный ход):**

| Поле | «+» означает | Со стика |
|---|---|---|
| `roll` | крен вправо (правый элерон вверх, левый вниз) | CH1: 2000 = вправо |
| `pitch` | нос вверх (руль высоты вверх) | CH2 с обратным знаком: 2000 = от себя = нос вниз |
| `yaw` | нос вправо (руль направления и колесо вправо) | CH4: 2000 = вправо |
| `flaps` | закрылки вниз (оба элерона вниз) | SwB (CH6): 0 или `FLAPS_DEPLOYED_US`, плавно за `FLAPS_TRANSITION_MS` |

ПИД считает `ошибка = цель − факт`: крен вправо (roll > 0) → отрицательная
команда крена → самолёт выравнивается. Коррекции автопилота прибавляются к
команде стиков **до** микшера, в тех же знаках.

**4. Команда → PWM.** `ControlMixer::mix()` считает отклонение задней кромки
каждой поверхности (элероны: вниз = «+», левый = `flaps + roll`, правый =
`flaps − roll`; руль высоты: вверх = «+»; руль направления: вправо = «+») и
переводит в PWM `1500 ± отклонение`, меняя знак для серво с
`Config::*_REVERSED = true`. Значения по умолчанию повторяют прежнее
поведение прошивки для стиков. Проверка на собранном самолёте — в
предполётном чек-листе [`PILOT_GUIDE.md`](PILOT_GUIDE.md). Реверс нужно
менять в `Config.h`, **а не на пульте** — иначе стик и автопилот разойдутся.

## Карта RC-каналов, ARM и failsafe

Источник — `include/Channels.h`. Пульт FS-i6 (10 каналов, режим 2) +
приёмник FS-iA6B, iBUS 115200.

| Канал | Орган пульта | Имя | Назначение |
|---|---|---|---|
| CH1 | правый стик ←→ | `AILERON` | Крен |
| CH2 | правый стик ↑↓ | `ELEVATOR` | Тангаж |
| CH3 | левый стик ↑↓ | `THROTTLE` | Газ, полный ход; < 950 = failsafe приёмника |
| CH4 | левый стик ←→ | `RUDDER` | Руль направления + рулевое колесо (одна серва) |
| CH5 | SwA | `ARM` | ≥ 1750 = ARM (на FS-i6 это тумблер вниз, к себе) |
| CH6 | SwB | `FLAPS` | ≥ 1750 = закрылки выпущены (флапероны) |
| CH7 | SwC (3 положения) | `AUX_2` | Режим: < 1250 MANUAL, 1250–1749 STABILIZE, ≥ 1750 AUTO_TAKEOFF |
| CH8 | SwD | `AUX_3` | Свободен |
| CH9 | VrA | `AUX_4` | Свободен |
| CH10 | VrB | `AUX_5` | Свободен |

**ARM** (`ArmingManager`): переход тумблера OFF→ON, газ < `THROTTLE_LOW_US`,
пройдены проверки датчиков для текущего режима. Иначе — отказ с причиной в
Serial, нужен новый цикл OFF→ON. Включение платы с тумблером в ON не армит.
OFF — DISARM сразу. Пока не armed, газ на ESC принудительно `PWM_MIN`.

**Потеря связи** (`IBusReceiver::isSignalLost()`):

1. Нет кадров дольше `RX_TIMEOUT_US` (500 мс) — обрыв провода/питания
   приёмника.
2. Газ < `RX_FAILSAFE_THROTTLE_US` (950) — failsafe, заданный в пульте.
   **FS-iA6B при потере пульта кадры не прекращает**, а повторяет последние
   значения (проверено на стенде), поэтому без настройки failsafe в пульте
   потеря связи не распознаётся. Настройка — в `PILOT_GUIDE.md`.

В failsafe: рули в нейтраль, газ `FAILSAFE_THROTTLE`, режим с CH7 не
переключается, датчики продолжают читаться. ARM не сбрасывается — после
восстановления связи самолёт снова слушается стиков.

## Данные датчиков

Структуры — в `include/sensors/SensorInterface.h`.

### `ImuData`

| Поле | Единица | Смысл |
|---|---|---|
| `gyroX`, `gyroY`, `gyroZ` | °/с | Угловые скорости в осях самолёта, авиационные знаки (см. выше) |
| `accelX`, `accelY`, `accelZ` | g | Ускорение в осях самолёта X к носу, Y влево, Z вверх |
| `roll`, `pitch` | ° | Комплементарный фильтр (α = 0.98, τ ≈ 0.1 с); стартуют сразу с угла по акселерометру |
| `yaw` | ° | Интеграл гироскопа, медленно уплывает; начальное значение — курс компаса |
| `temperature` | °C | Температура кристалла (формула под MPU6050 или MPU6500) |
| `timestamp` | мкс | `micros()` момента чтения |

Калибровка IMU (при каждом старте и командой `i`): 2 с неподвижно, гироскоп
→ нулевое смещение, акселерометр → **текущее положение становится
горизонтом**.

### `BarometerData`

| Поле | Единица | Смысл |
|---|---|---|
| `pressure` | Па | Давление |
| `temperature` | °C | Температура датчика |
| `altitude` | м | Высота **относительно точки калибровки** (при старте); формула `44330·(1 − (P/P0)^0.1903)` |
| `verticalSpeed` | м/с | Производная высоты по реальным отсчётам (50 Гц) через ФНЧ τ = 0.5 с |
| `timestamp` | мкс | Момент последнего нового отсчёта |

### `MagData`

| Поле | Единица | Смысл |
|---|---|---|
| `magX`, `magY`, `magZ` | мкТл | Поле по осям чипа, после вычета hard-iron смещений |
| `headingDegrees` | ° (0..360) | `atan2(magY, magX)`, без компенсации наклона; направление отсчёта ещё не проверено на собранном самолёте |
| `timestamp` | мкс | Момент чтения (50 Гц) |

### `GpsData`

| Поле | Единица | Смысл |
|---|---|---|
| `latitude`, `longitude` | ° | Из UBX-NAV-PVT |
| `altitude` | м | Над уровнем моря (hMSL) |
| `groundSpeed`, `heading` | м/с, ° | Путевая скорость и курс по земле |
| `numSatellites`, `fixType` | — | 0 = нет фикса, 2 = 2D, 3 = 3D |
| `horizontalAccuracy`, `verticalAccuracy` | м | Оценки точности модуля |

**Что значит `isAvailable()`.** Для I2C-датчиков — датчик ответил при
`begin()` **и** последние чтения не проваливаются подряд (MPU — ~0.1 с,
барометр и компас — ~0.5 с без ответа). При сбое чтения данные не
затираются мусором: остаются прошлые, растёт счётчик ошибок (виден по
команде `s`). Для GPS — хотя бы один валидный NAV-PVT, и последний не
старше `GPS_TIMEOUT_US`.

**Если датчика нет** (`nullptr` или `isAvailable() == false`), `Autopilot`
не даёт коррекций, а самолёт управляется как в MANUAL. `main.cpp`
калибрует только ответившие датчики.

## Разбор FlightController::update()

Вызывается из `loop()` каждые 2 мс. Порядок и есть приоритет:

1. **`receiver.update()`** — разбор накопившихся байтов iBUS.
2. **Потеря связи и газ пилота.** `receiverFailsafe = receiver.isSignalLost()`,
   `pilotThrottle = throttle.update(rc, receiverFailsafe)`.
3. **Режим** — `modeSelector->update(rc)`, только при живой связи (в
   failsafe-кадре CH7 не отражает тумблер).
4. **Датчики и автопилот** — `autopilot->update(armed && !failsafe,
   pilotThrottle)` **всегда**, даже в failsafe: фильтры углов не должны
   застывать. Пока не armed, ПИД работает (рули отвечают на наклон — удобно
   на столе), но интегратор держится на нуле.
5. **Failsafe** — если связь потеряна: `outputs.setFailsafe()` (рули 1500,
   газ 1000) и `return`. Абсолютный приоритет над всем ниже.
6. **ARM** — `arming.update(rc, false)`.
7. **Команда** — `mixer.fromSticks(rc, millis())` (стики + плавные закрылки) + `getRollCorrection()`/
   `getPitchCorrection()` автопилота, ограничение ±500.
8. **Микшер** — `mixer.mix(command)` → PWM элеронов (закрылки + крен), руля
   высоты и руля направления с учётом реверса.
9. **Газ** — `autopilot->applyThrottle(pilotThrottle)`: MANUAL/STABILIZE —
   газ пилота; ALT_HOLD — газ пилота + поправка ПИД высоты;
   AUTO_TAKEOFF — max(газ пилота, программа взлёта). Затем, если не armed, —
   принудительно `PWM_MIN`. Эта проверка стоит последней, чтобы ни один
   режим не протащил газ мимо ARM.
10. **`outputs.write(output)`** — PWM на 4 выхода.

`{ "mode": 1 }` — `0` MANUAL, `1` STABILIZE, `2` AUTO_TAKEOFF, `3` ALT_HOLD.

`{ "kpRoll": 5, "kiRoll": 0.5, "kdRoll": 0.5 }` — любое из полей `kpRoll`,

HTML-дашборд: бары 10 каналов, ARM/связь, выходы, датчики, кнопки режимов,
форма ПИД. Опрашивает `/api/status` каждые 200 мс.

## Консоль и диагностика

Монитор порта — 115200, разъём «COM». Команды — буква + Enter; калибровки и
`p` работают только когда не armed.

| Команда | Что делает |
|---|---|
| `h` | Список команд |
| `s` | `printStatus()` всех датчиков: данные, счётчики ошибок I2C, состояние калибровки |
| `i` | Калибровка IMU (2 с неподвижно) |
| `m` | Калибровка компаса (15 с вращения), сохраняется в NVS |
| `p` | Самопроверка выходов: реальный импульс на каждом выходе против ожидаемого |

Отладочный вывод:

- `IBUS: ... | RX=OK / LOST(нет кадров) / LOST(failsafe пульта) | ARM=... | OUT ...`
  и строка автопилота — раз в 100 мс, только при изменениях (шум датчиков
  отсекается порогами).
- `SYS: loop 500 Hz, avg ... us, max ... us | iBUS ok=... crc_err=... | heap ... | uptime ...`
  — раз в 10 с.

## Как добавить новый датчик

### A) Ещё один чип существующей категории

1. Создайте `include/sensors/<Имя>_Sensor.h`, реализуйте методы `Sensor`
   (`begin()`, `isAvailable()`, `update()`, `getSensorType()`,
   `printStatus()`) и своей категории. Конструктор принимает шину из HAL
   (`II2CBus&`, `ISpiBus&` + CS, `IUartPort&`), **не** `Wire`/`SPI` напрямую.
2. Для I2C используйте `readRegisters()`/`writeRegister()` из `II2CBus` —
   они проверяют ответ устройства. При сбое чтения не затирайте данные,
   считайте ошибки, как `MPU6050_Sensor`.
3. Данные — в соглашении о знаках проекта (для IMU — с поворотом
   `IMU_ROTATION_CW_DEG` и авиационными знаками, см. `MPU6050_Sensor.h`).
4. Добавьте ветку в `SensorSelection.h`: `#define SENSOR_<КАТЕГОРИЯ>_<ИМЯ>`,
   `using Selected... = ...;` и `#define SELECTED_..._ARGS(board) ...`.
   `main.cpp` при смене датчика не трогается.
5. Соберите все три окружения и проверьте на железе.

### B) Новая категория

1. Структура данных и интерфейс — в `SensorInterface.h` по образцу
   `GpsSensor`/`GpsData`.
2. Дальше как в A, плюс nullable указатель в конструктор `Autopilot` (без
   датчика — никаких эффектов, а не падение) и поля в `GET /api/status` с
   парой `attached`/`available`.

### Новая шина или периферия

Новый интерфейс в `include/hal/`, реализация в `include/hal/esp32/`, доступ
через `IBoard`.

## Как добавить новый режим автопилота

1. Новое значение в `enum AutopilotMode` (`Autopilot.h`) и строка в
   `modeToString()`.
2. Обработчик `handle<Режим>Mode()` и ветка в `Autopilot::update()`. Без
   нужного датчика — нулевые коррекции. Интегратор копите только когда
   `armed` (передавайте его в `PID_Controller::calculate()`).
3. Если режим управляет газом — ветка в `Autopilot::applyThrottle()`.
   `FlightController` при этом не меняется.
4. Выбор с пульта — в `AutopilotModeSelector::modeFor()`; с дашборда —
   кнопка в `WebDebugServer::handleRoot()` и проверка диапазона в
   `handleSetMode()`; короткое имя — в `OledDisplay::shortMode()`.
5. Если режиму нужны датчики — проверка в
   `ArmingManager::checkFailureReason()`.
6. Проверка на столе без винта: рули должны отвечать на наклон в сторону
   выравнивания.

## Как добавить новую плату

1. `[env:<имя>]` в `platformio.ini` с уникальным `-D BOARD_ESP32_<ИМЯ>`.
2. Блок `#elif defined(BOARD_ESP32_<ИМЯ>)` в `Config.h` со всеми пинами,
   включая `PIN_I2C2_SDA/SCL` (−1, если OLED нет). Посчитайте бюджет GPIO
   заранее: flash/PSRAM/USB/strapping.
3. Выходам серво нужны 5 каналов LEDC — есть на всех ESP32. Если под
   руль направления нет пина — `PIN_RUDDER = -1`, выход просто отключится.
4. `default_envs` не меняйте, пока плата не проверена на железе; в коммите
   явно отметьте, если распиновка не проверена.

## Известные ограничения

- **Автопилот не испытан в полёте.** На столе знаки проверены вживую
  (наклон → коррекция в сторону выравнивания), коэффициенты ПИД — стартовые.
- **STABILIZE — выравнивание поверх стиков**, а не «угловой режим»
  (FBWA), где стик задаёт угол крена/тангажа. Пилот и автопилот суммируются.
- **Failsafe — рули в нейтраль и мотор в ноль.** Для самолёта лучше
  планирование с выровненными крыльями по IMU — запланировано.
- **Горизонт = положение при включении.** IMU калибруется при каждом старте;
  включать нужно ровно и неподвижно. Сохранённой в NVS калибровки уровня нет.
- **Компас:** курс без компенсации наклона, направление отсчёта не проверено
  на собранном самолёте, калибровку надо делать уже в самолёте. Ни один
  режим курс пока не использует.
- **GPS** не используется для навигации; на ESP32-C3 — только приём.
- **`ICM42688_Sensor.h` не приведён к соглашению о знаках** и не проверен на
  железе — доработать при подключении.
- **`BMP388_Sensor.h` (SPI) и `BMP388_I2C_Sensor.h`** дублируют компенсацию;
  опрос по флагу готовности и ФНЧ есть только в I2C-версии.
- **I2C на макетке ловит помехи** от ESC/мотора (единичные ошибки видны по
  `s`). Драйверы их переживают, но в самолёте провода I2C — короткие и
  подальше от силовых.
- **ESP32Servo не используется.** Версия 3.2.1 на ESP32-S3 раскладывает сервы
  по MCPWM и в `attachPin()` путает номер блока MCPWM с номером таймера:
  GPIO6/7 выдавали сигнал GPIO4/5 (ESC управлялся правым стиком). Выходы
  переписаны на LEDC; возвращать библиотеку — только проверив `p`.
- **ESC — 50 Гц PWM**, режима калибровки диапазона газа в прошивке пока нет.
- **Веб-дашборд:** пароль точки доступа слабый, команды принимаются и в
  полёте. Это инструмент для стенда и поля, не для полёта.
- **Механика прототипа:** первый прототип летал, выявлены слабое крепление
  мотора и недостаточная жёсткость крыла.
- **Лицензия не выбрана** — не указывайте её в коде и документации, пока это
  не решено.

## Как вносить изменения

- **Маленькие коммиты:** один логический шаг — один коммит.
- **Собирайте все три платы** после правок в общем коде — S3 основная, но C3
  и dev не должны ломаться.
- **Проверяйте на железе то, что можно проверить:** знаки — наклоном,
  выходы — командой `p`, связь — выключением пульта.
- **Не выдумывайте API.** Сверяйтесь с исходниками фреймворка в
  `~/.platformio/packages/framework-arduinoespressif32/` (Arduino core 2.0.x)
  — интернет часто описывает версию 3.x с другим API (например, LEDC).
- **Не приукрашивайте статус.** Не проверено на железе — так и пишите.
- **Слой не должен знать больше положенного.** Если нижнему классу вдруг
  понадобился верхний — логика должна подняться в `FlightController`.
- **Меняя контракт данных** (`FlightOutputState`, `ControlCommand`,
  `ImuData`, JSON `/api/status`) — обновляйте всех потребителей в том же
  коммите.
