## 1. 現状：正直に

OpenPlaneProject は現在、すでに飛行したものの未成熟なグライダーの試作機で、ESP32 上に独自のファームウェアを載せています。完成品ではなく、自律ドローンでもありません。ハードウェアは、翼幅 1200 mm、翼弦 250 mm、翼型 NACA 4412、PETG 製の構造体（3D プリント）、MG90S サーボ（エルロンごとに 1 個ずつ）、3S LiPo 電源です。最初の試作機（ESP32-C3、D2212 1000KV モーター、40A の ESC）はすでに手動操縦で飛行し、飛行後に具体的な問題が見つかりました。モーターと主翼の取り付けの強度不足（カーボンで補強が必要）と、サーボの調整の必要性です。

現在の機体は ESP32-S3（N16R8）に移行しており、D3548 1100KV モーターと 60–80A の ESC を使い、ベンチ上でオートパイロットのすべてのセンサーを接続しています。IMU（MPU6500）、気圧センサー BMP388、コンパス QMC5883P、そして OLED の状態表示です。実機で確認済みのもの：iBUS 経由の手動 RC 操縦（エルロン、昇降舵、方向舵（ステアリング可能な車輪付き）、フラップ（フラッペロン）のミキサー込み）、独立したスイッチによる ARM、送信機の電源を切ったときのフェイルセーフ、500 Hz の制御周期、Wi-Fi 経由のライブ Web ダッシュボード。机の上では、スタビライゼーションが傾きに正しい向きで反応します。

その後、ファームウェアには 12 のオートパイロットモード（スタビライゼーション、高度保持、クルーズ、GPS による円旋回とホームへの帰還、手投げ発進、自動着陸、サーマルでのソアリング、「レスキュー」）、ジオフェンス、信号喪失時のホーム帰還、ペイロード投下、2 つの気圧センサーによるピトー管、新しいセンサー（LSM6DSV、ICM-45686、QMC6309、SPL06、BMP581）への対応、そして QGroundControl 向けの MAVLink テレメトリーを備えた STM32H743 用の完全なファームウェアが加わりました。これらはすべて、387 件の自動テストと閉ループのフライトシミュレーション（ファームウェア全体が飛行機のモデルを操縦します）で検証済みですが、**空ではまだ試験していません**。言い換えると、これまでに飛んだのは手動操縦だけです。オートパイロットは書き上がっていて、飛ばさずに確認できることはすべて確認しており、飛行試験を待っている状態です。

## 2. なぜ重要か

参入障壁の低い自律型の小型航空機は、最大積載量や航続距離ではなく、反応の速さと運用コストの低さが決め手になる仕事をカバーします。

- **到達困難な地域や被災地への医薬品・血液の配送**：流された道路、インフラの不在、自然災害や紛争のあとの破壊。ここで決め手になるのは積載量ではなく（荷物は小さい）、反応までの時間です。車や徒歩で 1 日かかるところを、数分から数時間にします。
- **捜索救助活動**：地上班が到着する前に、被災者へ装備、救急キット、通信機器、浮き具をピンポイントで投下します。ヘリコプターが高価すぎる、あるいは天候や地形のせいで使えない場所が対象です。
- **精密農業**：作物のモニタリングと、必要な場所への薬剤の散布・施用。この種の仕事向けの閉じたドローンプラットフォームは数千ドルからで、中小の農家には採算が合いません。

3 つの分野に共通する経済は同じです。「解決策はあるが、高価で閉じている」と「高価なので、実質的に解決策がない」の差であり、安価でオープンなプラットフォームが狙うのはまさにこの隙間です。これは適用分野と市場の課題の説明であり、OpenPlaneProject がすでに貨物を届けられるという主張ではありません。現段階では、目標と、その目標に取り組む価値がある理由についての表明です。

## 3. 投資テーゼ：オープンな ESP32 アーキテクチャがなぜ非対称な強みになるのか

配送・モニタリング向けの商用の自律ドローンプラットフォームは、たいてい閉じたフライトコントローラーと閉じたソフトウェアの上に作られ、機体 1 台あたり数百〜数千ドルかかり、機体群の運用にはライセンス料やサービス契約が必要です。OpenPlaneProject は別の前提から出発します。

- **安価な土台。** ESP32 モジュールは 5〜15 ドル程度で、周辺（MG90S サーボ、ESC、iBUS 受信機）はホビー向けの標準部品です。閉じた商用プラットフォームの入場券より 1 桁安く、予算の限られた環境でのパイロット導入（NPO、小規模農業、地域の救助機関）には決定的です。
- **オープンなコードは信頼の経済を変えます。** 医療配送のために機体群を導入する組織は、安全性（failsafe、ARM のロジック）を監査し、特定のベンダーとそのロードマップに依存することなく、自分たちのセンサーや規則に合わせてファームウェアを調整できます。
- **アーキテクチャは今日の時点で、現在のグライダーだけでなく拡張を見据えて設計されています。** これは宣言ではなく、コードの構造から直接導かれることです。
  - 新しいセンサーは、既存のインターフェース `Sensor` → `ImuSensor`/`BarometerSensor`（`include/sensors/SensorInterface.h`）を実装するクラスとして、コアを変更せずに追加できます。IMU（MPU6050/MPU6500、ICM-42688）、気圧センサー（BMP388、BME280）、コンパス（QMC5883P/L）、GPS（u-blox M10）のドライバーはすでにこの方法で作られています。いずれもバスのレジスタを直接たたく形で書かれ（インターフェース `II2CBus`/`ISpiBus`/`IUartPort`）、外部ライブラリを使っていないため、特定ベンダーの SDK への隠れた依存もありません。
  - 新しいボードは、`include/config/Config.h` に `#elif` ブロックを 1 つ、`platformio.ini` に `[env:...]` ブロックを 1 つ足すだけで追加できます。ボードの切り替えは、すでに 4 つのターゲットで動いています（下の表を参照）。仮定の話ではありません。
  - `Autopilot.h` はすでに `ImuSensor*`/`BarometerSensor*` をパラメーターとして受け取ります（`nullptr` でも構いません）。つまり、オートパイロットとハードウェアの間の取り決めは、センサーの構成が変わることを前提にしています（次のステップは、同じパターンのもう 1 つのクラスとしての GPS です。フェーズ 3 を参照）。
  - `WebDebugServer.h` はすでに、集約された 1 つの JSON（`GET /api/status`）を返し、コマンド（`POST /api/setmode`、`/api/setpid`）を受け付けます。つまり「機体がテレメトリーを返し、コマンドを受け付ける」というプロトコルはすでに存在し、地上局はゼロから書くのではなく、これを土台に育てていくことになります。

非対称性とは、このプラットフォームの参入障壁（資金、新しい仕事に合わせるための時間）が、閉じた競合より 1 桁低いことです。しかも、自律性への道のりはコアの書き直しを必要とせず、既存のインターフェースの上に新しいクラスを足すだけで済みます。これはオープンなエンジニアリングの土台であり、完成した商用製品ではありません。したがって、投資家・パートナーに向けたテーゼは「完成品を買ってください」ではなく、「土台がすでに検証され、次のステップが技術的に明確になった段階で参加してください」です。

## 4. 現在のアーキテクチャ：以降のフェーズの土台

### 4.1 対応ボード

ボードの選択は PlatformIO のビルドオプション 1 つで、ボードを切り替えてもロジックの修正は要りません（`include/config/Config.h` + `platformio.ini`）。

| 環境（`pio run -e ...`） | ボード | 状況 | aileron L / R | elevator | esc | ibus_rx | i2c sda / scl |
|---|---|---|---|---|---|---|---|
| `esp32-s3`（default） | ESP32-S3 N16R8（DevKitC-1） | **メイン。ベンチですべてのセンサーを接続して確認済み** | GPIO4 / GPIO5 | GPIO6 | GPIO7 | GPIO17 | GPIO41 / GPIO42 |
| `esp32-c3` | ESP32-C3 SuperMini | 最初の試作機。手動操縦で飛行した | GPIO5 / GPIO4 | GPIO6 | GPIO7 | GPIO8 | GPIO1 / GPIO3 |
| `esp32-dev` | 標準の ESP32 38 ピン | ベンチ用。**実機では未確認**（ファームウェア全体はテストで動作） | GPIO13 / GPIO14 | GPIO27 | GPIO26 | GPIO16 | GPIO21 / GPIO22 |
| `stm32h743` | STM32H743VIT6（WeAct Mini） | 完全なファームウェア + MAVLink。**ボードはまだない**（ファームウェア全体は PC 上のテストで動作） | PA0 / PA1 | PA2 | PA3 | PE7 | PB11 / PB10 |

ファームウェアの書き込み：`pio run -t upload`。モニター：`pio device monitor`（115200）。

### 4.2 RC チャンネルの割り当て（FS-i6 + FS-iA6B、iBUS、10 チャンネル、1000–2000 µs）

| チャンネル | 名前 | 既定の用途 |
|---|---|---|
| CH1–CH4 | スティック | ロール、ピッチ、スロットル、方向舵 |
| CH5 | ARM | スイッチ SwA：スロットルが下のとき ARM、DISARM は即時 |
| CH6 | SWB | フラップ |
| CH7 | SWC | モード：MANUAL / STABILIZE / AUTO_TAKEOFF |
| CH8 | SWD | RTH：ホームへ |
| CH9 | VRA | スタビライゼーションの強さ |
| CH10 | VRB | クルーズ速度 |

CH6–CH10 は `include/config/Controls.h` の 1 行で割り当てます。12 のモードのどれでも、10 の機能（フラップ、ブレーキ、ペイロード投下、ジオフェンスなど）、7 つのダイヤルを選べます。詳しくは [AUTOPILOT_GUIDE.md](AUTOPILOT_GUIDE.md) を参照してください。

### 4.3 制御の流れ（`FlightController::update()`）

オーケストレーターは 1 つで、順序は固定、ループは 500 Hz の固定周期です。iBUS 受信 → パイロットのスロットル → CH7 からのモード → **センサーの読み取りとオートパイロットの計算（常に、通信がなくても）** → **最優先での信号喪失チェック**（空中では、GPS があればモーターを回したままホームへ、GPS がなければ翼を水平にして滑空。地上では舵面をニュートラルに）→ ARM → スティックの指令 + オートパイロットの補正（統一した航空機の符号で）→ サーボのリバースを含むミキサー → モードのスロットル → ARM なしでのスロットル遮断 → サーボ/ESC への書き込み。この順序の規律（まず安全、次に手動操縦、そのうえに載せるものとしてオートパイロット）こそが、基本のループを書き直さずに、より自律的な動作を安全に組み込める理由です。Wi-Fi、ダッシュボード、画面は 2 つ目のコアで動き、制御を遅らせません。

### 4.4 Web ダッシュボード：地上局の原型

`WebDebugServer.h` は現時点でもアクセスポイント（SSID `OpenPlane-Debug`、IP `192.168.4.1`）を立ち上げ、JSON を返したり受け付けたりします。

| メソッドとパス | 内容 |
|---|---|
| `GET /api/status` | 集約された 1 つの JSON：RC（10 チャンネル）、armed/failsafe、7 つの出力（`us`、`attached`）、IMU、気圧センサー、コンパス、GPS、ピトー管（それぞれに `attached`/`available` + データ）、オートパイロット（モード、補正、PID、ナビゲーション、有効な機能） |
| `POST /api/setmode` | `{mode: 0-11}`：オートパイロットのモードを切り替える |
| `POST /api/setpid` | `{kpRoll, kiRoll, kdRoll, kpPitch, kiPitch, kdPitch}`：どのフィールドも省略できる |
| `GET /` | HTML ダッシュボード：10 チャンネルのライブバー、各出力/センサーの状態、モードのボタン、PID のフォーム |

JSON の `attached`/`available` フィールドは常に含まれます。ダッシュボードは、センサーがないことを黙っているのではなく、「構成に含まれていない」ものと「構成に含まれているが応答しない」ものを区別して正直に表示します。これは、この文書全体の土台にある誠実さの原則と同じで、望ましい状態を実際に動いているかのように見せないということです。

## 5. フェーズごとの技術ロードマップ

以下は 8 つのフェーズです。それぞれ、すでにあるクラスの上に積む次の論理的な一歩として書いてあり、作り話の日付や金額は含めていません。

### フェーズ 1 — 手動操縦と安全な土台 [完了]

**目標**：透明性のあるデバッグを備えた、信頼でき予測しやすい RC グライダー。**技術的にすでにあるもの**：`IBusReceiver.h` の、信号喪失を検知する iBUS 解析、ミキサー `ControlMixer.h`（スティック → ロール/ピッチ/フラップの指令 → サーボのリバースを含む PWM。UART/PWM のことは何も知らない）、`ThrottleManager.h`、`ArmingManager.h`（スロットルが下のとき独立したスイッチで ARM、DISARM は即時）、`FlightController.h` の絶対優先のフェイルセーフ、Serial への出力（`DebugLogger.h`）、Web ダッシュボード（`WebDebugServer.h`）と OLED 画面（`OledDisplay.h`）。**これが他のすべての土台である理由**：これは常に動かなければならない唯一の層であり、ほかのフェーズがまだ実装されていなくても、そのセンサーが外されていても変わりません。だからこそフェイルセーフと ARM を最初に書き、実機で確認しました（送信機の電源を切ったときの FS-iA6B 受信機の実際の挙動を含む）。

### フェーズ 2 — IMU + 気圧センサー → オートパイロット [書き上げ済み。テストとシミュレーションで検証済み、飛行試験待ち]

**目標**：最初の自律飛行モード。水平の安定化、自動離陸、高度保持。**技術的にすでにあるもの**：`imu/MPU6050_Sensor.h`（MPU6050 と MPU6500、レジスタを直接操作、基板の取り付けに合わせた軸の回転、航空機の符号、`ImuSensorBase` の相補フィルター）、`baro/BMP388_Sensor.h`（I2C または SPI、Bosch の完全な補償、データ準備完了フラグによる読み出し、フィルター済みの垂直速度）、`PidController` を持つ `Autopilot.h`（D 項はジャイロから、積分器は ARM の後にだけ蓄積）と 12 のモード（MANUAL から SOARING と RESCUE まで）。モードは `Controls.h` の表に従ってスイッチで、Web ダッシュボードから、そして QGroundControl から切り替えられ、さらにフェイルセーフ（ホームへの帰還または滑空）もあります。どのモードも、ファームウェア全体が機体モデルを操縦する閉ループのシミュレーションで飛びます（`test/native/test_sim`）。ESP32-S3 を載せたベンチではすべてのセンサーが応答し、符号は実機で確認済みです。傾ける → 舵面が水平に戻す側へ補正する。**このフェーズを完了するために必要なこと**：電子部品を機体に移し、組み上げた機体で舵面の向きを確認し、最初の飛行試験を行うこと。最初は安全な高度での STABILIZE から始めます。

### フェーズ 2.5 — 実機からのフィードバック [土台。シミュレーションで検証済み]

**目標**：オートパイロットが、ある 1 つの速度に合わせて決めた係数ではなく、実際の飛行機がいまこの瞬間に舵へどう反応しているかに従って動くようにすること。フェーズ 2 の PID は舵を「式どおり」に振るだけで結果を確認しません。低速では補正が足りず、高速では効きすぎます。**技術的にすでにあるもの**（`include/autopilot/feedback/`、ファームウェアには**接続していません**）：飛行中の舵面の効きの推定（再帰最小二乗法、速度に応じた再計算 ∝ V²）、「角度 → 回転速度 → 舵」のコントローラー（追い込み補正付き：「舵が最後まで切れていない場合は、さらに切る」）、速度低下と失速に対する保護（スロットル、機首下げ、翼水平）、滑走路または手投げでの離陸と、センサーによる段階的な着陸。すべてをボード上で、飛行機の閉ループシミュレーションにより検証しています（`pio test -e esp32-s3 -f test_feedback`、10 シナリオ）。エルロンの接続逆転、乱気流、低スロットルでの機首上げ、離陸と着陸も含みます。**このフェーズを完了するために必要なこと**：フェーズ 2 の最初の飛行のあとで、「シャドウモード」（フィードバックは、もし動作させたらどうしたかをログに書くだけ）、続いて 1 軸ずつの接続、対気速度センサー（ピトー管）、接地前の引き起こし用の測距センサー。詳しくは [`DEVELOPER_GUIDE.md`](DEVELOPER_GUIDE.md) の「フィードバック」の節を参照してください。

### フェーズ 3 — GPS とコンパス [ファームウェアに実装済み。シミュレーションで検証済み]

**状況（更新）：ナビゲーションは動作しています**。GPS/コンパス/ジャイロによるヒステリシス付きの針路、ARM 時のホーム設定、CRUISE、LOITER（円周へ収束するベクトル場）、RTH、ジオフェンスがあり、閉ループのシミュレーションで検証済みです。以下はこのフェーズの当初の記述です。GPS（u-blox M10、`sensors/gps/UbloxM10_Gps.h`、UBX-NAV-PVT プロトコル）と磁気センサー（「GY-273」ボードの 2 種類：QMC5883P は `sensors/mag/QMC5883P_Sensor.h` で、現在のベンチに載っており実機で確認済み、QMC5883L は `sensors/mag/QMC5883L_Sensor.h`）は、IMU や気圧センサーと同じ考え方で、インターフェース `GpsSensor`/`MagnetometerSensor`（`include/sensors/SensorInterface.h`）を実装する新しいクラスとして追加しました。`Autopilot.h` と `FlightController.h` は書き換えておらず、同じ方法（コンストラクターの null 許容ポインター）でデータ源が 2 つ増えただけです。ついでに HAL の層（`include/hal/`）ができ、センサーはこれを通してバスにアクセスします。I2C/SPI/UART は、ESP32 固有の `Wire`/`SPI`/`HardwareSerial` に直接結び付かなくなりました。

現時点では、GPS/コンパスのデータは `Autopilot::getGpsSensor()`/`getMagnetometerSensor()` と `GET /api/status` から取得でき、起動時にコンパスから初期の yaw を 1 回だけ設定しますが、**制御には使われていません**。このフェーズを完了するための未解決の課題：GPS モジュールを ESP32-S3 に接続すること（UART2 のピンはすでに確保済み）、組み上げた機体でコンパスを校正すること、針路に傾きの補償を加えること。ESP32-C3 では本格的な GPS は不可能です。TX 用の GPIO が足りません（`DEVELOPER_GUIDE.md` のピン配置を参照）。

### フェーズ 4 — 経由地点に沿った飛行（waypoint navigation）[次のステップ]

**状況**：基本機能は揃っています。`Guidance::rollForCourse`、点の周りの円旋回、点への帰還（RTH）、ミッションを転送するための MAVLink チャンネル（現時点では、ミッションを要求されると機体は正直に「0 地点」と答えます）。残っているのは、ルートの保存、地点間の遷移、MAVLink の MISSION_* プロトコルです。

**目標**：オペレーターがルートの各区間で操作しなくても、機体が指定された座標の列に沿って飛ぶこと。**アーキテクチャへの収まり方**：`Autopilot.h` に新しい `AutopilotMode` を加えるだけで、既存の MANUAL/STABILIZE/AUTO_TAKEOFF/ALT_HOLD と同列になります。つまりモード切り替えの仕組み（RC のスロットと `POST /api/setmode` 経由）は変わらず、5 つ目のモードが加わり、RC からの手動入力の代わりに GPS（フェーズ 3）から針路と距離を取ります。**技術的に必要なこと**：ある点への針路を計算するアルゴリズムと、ルート上の地点間を移る処理、そしてルートそのものを機体に転送する方法です（自然な候補は、すでにモードや PID の操作に使っている同じ HTTP API の拡張です）。

### フェーズ 5 — 長距離テレメトリー [STM32 のファームウェアで完了]

**状況**：STM32H743 では、無線モデム経由の MAVLink 2（SiK、MAVLink モードの ELRS）で、姿勢、位置、速度、モード、PID パラメーター、地上からのモード変更が使えます。フレームは基準実装の pymavlink と突き合わせ済みです。ESP32 には空いている UART がないため、Wi-Fi ダッシュボードを使います。以下はこのフェーズの当初の記述です。

**目標**：ベンチ上ではなく、実際の配送で意味を持つ距離での機体↔地上の通信。**現状の正直な評価**：`WebDebugServer` の Wi-Fi アクセスポイントは、現時点でも集約したステータス全体と制御コマンドをやり取りできますが、通常の Wi-Fi AP の到達距離は数十メートルで、机の上や飛行場でのデバッグには足りても、目視外の自律ルートには足りません。**技術的に必要なこと**：`GET /api/status` で定義済みのデータ形式をそのまま運ぶ、より長距離の別の無線チャンネル（たとえば LoRa モジュールや専用のテレメトリー無線モデム）。つまり、トランスポート層の置き換えまたは追加であり、テレメトリーの形式の書き直しではありません。

### フェーズ 6 — 本格的な地上管制 GUI [一部実現：QGroundControl / Mission Planner]

**状況**：MAVLink のおかげで、標準的な地上局はすでに機体を認識します（地図、ホーム地点、計器、ArduPlane の名前で表示されるモード）。機体群向けの独自の地上局は、引き続き目標です。以下はこのフェーズの当初の記述です。

**目標**：1 機のデバッグページではなく、地図、ライブのテレメトリー、機体群の管理を備えたミッション計画局。**アーキテクチャへの収まり方**：`WebDebugServer.h` は現時点でもダミーではなく、集約した JSON ステータスとコマンド API を持つ動作中の Web サーバーです（4.4 節の表を参照）。これが出発点であり、捨てなければならないものではありません。次のステップは、現在位置を表示する地図（フェーズ 3 のあと）、ルートの表示とアップロード（フェーズ 4 のあと）、長距離の無線チャンネル上での動作（フェーズ 5 のあと）、そして画面を 1 機から複数機へ広げることです。詳しくは 6 節を参照してください。

### フェーズ 7 — ペイロード投下機構と配送向けの保護策 [ファームウェアに実装済み。飛行未実施]

**状況**：ペイロード投下（サーボ AUX1、任意のスイッチに割り当てられる機能 `PAYLOAD_DROP`）、ジオフェンス（半径と上限高度 → RTH）、信号喪失時のホーム帰還、「機体ロスト」のブザー。以下はこのフェーズの当初の記述です。

**目標**：プラットフォームを「自律的に飛ぶ飛行機」から「自律的に配送する飛行機」へ変えること。**技術的に必要なこと**：荷物の投下・払い出し機構用の追加サーボ（`FlightOutputs.h` のほかの出力と同じ考え方で制御）と、中立的な飛行ではなく配送に特有の保護策。つまり、ジオフェンス（飛行エリアの制限）と、信号喪失時の出発点への自動帰還です（現状では、空中で信号を失うと `FlightController` はモーターを止め、翼を水平にした滑空に移ります。これは手動操縦のグライダーとしては正しい動作ですが、自律配送では、ただ滑空するのではなく GPS で基地へ戻るのが論理的な次のステップです）。

### フェーズ 8 — 機体群への拡大

**目標**：複数の機体を同時に管理すること。タスクの割り振り、運用パネル、飛行履歴です。ここまで来ると、プロジェクトは単なる趣味の工学試作ではなく、事業課題としても興味深い運用ツールになります。複数機のルート計画、タスクのキュー、各機のリアルタイムの状態です。技術的にはフェーズ 3〜6（GPS、テレメトリー、GUI）の上に載る上位層で、実質的には同じ `WebDebugServer` の API を、1 つではなく多数のテレメトリー源に広げたものです。

## 6. GUI：デバッグページから地上局へ

この節の要点は、GUI をゼロから作る必要はなく、すでに一部が存在して動いているということです。`WebDebugServer.h` は現時点で次のことをします。

- 機体の状態を 1 つの集約した JSON スナップショットとして返します（`GET /api/status`）。RC チャンネル、armed/failsafe のフラグ、各出力の状態、各センサーの状態（正直に、`attached` と `available` という別々のフラグで）、そしてオートパイロットの状態です。
- 制御コマンド（モード変更、PID の調整）をリアルタイムで受け付けます。ファームウェアの書き直しは要りません。
- ライブのチャンネルバーと操作ボタンを備えた HTML ダッシュボードをそのまま返します。

本格的な地上局への道のりは、すでに動いているプロトコルを順に拡張していくことで、アーキテクチャの変更ではありません。

1. ダッシュボードに地図と現在位置を加える。同じ JSON ステータスのもう 1 つのフィールドとして GPS（フェーズ 3）が必要です。
2. ルートの作成とアップロードを加える。ウェイポイントモード（フェーズ 4）と、`/api/setmode`/`/api/setpid` と同様の POST API の拡張が必要です。
3. トランスポートを Wi-Fi AP から長距離リンク（フェーズ 5）へ移す。既存のフロントエンドを書き直さずに済むよう、メッセージの形式は同じままにします。
4. 画面を 1 機から複数のテレメトリー源へ広げる（フェーズ 8）。

言い換えると、将来の地上局のうち「ゼロから書く必要があるのか」という点で最もリスクの高い部分、つまり機体の状態のシリアライズとコマンド API は、すでに実装され、ボード上で実機確認済みです。

## 7. 正直な制約：まだ動かないもの

ロードマップが宣伝のように見えないよう、まだ実現していないこと、部分的にしか実現していないことを別に記します。

- オートパイロットは、ベンチ上で、387 件の自動テストと閉ループのシミュレーションにより検証済みですが、飛行では一度も試験していません。これまでに飛んだのは手動操縦だけです（最初の試作機で）。シミュレーションの機体モデルは単純化したもので、係数は初期値です。
- 新しいセンサー（LSM6DSV、ICM-45686、QMC6309、SPL06、BMP581）は、データシートに基づくレジスタエミュレーターで検証済みです。実機ではまだです。
- STM32H743：ファームウェア全体は PC 上で STM32duino のフェイクの上で動いています。実物のボードはまだありません。
- スタビライゼーションの基準となる水平は、電源投入時の機体の姿勢（IMU は起動のたびに校正されます）か、3 つの姿勢による取り付け校正です。
- サーボの物理的な接続はソフトウェアからは見えません。見えるのは、パルスが実際にピンから出ていることだけです（コンソールからの自己診断）。
