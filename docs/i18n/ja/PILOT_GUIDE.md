## 必要なハードウェア

現在の構成のキットです（ファームウェアはこの構成で検証しました）。

- **STM32H743 ボード DevEBox H743**（MCUDEV）：メインボード。以前のメインボードである下の ESP32-S3 も引き続きサポートしています。
- **ESP32-S3 N16R8 ボード**（USB-C が 2 つ付いた DevKitC-1 のクローン。「USB」と「COM」）。
- **FS-i6 送信機＋FS-iA6B 受信機**（iBUS プロトコル、10 チャンネル）。必要なデータ線は 1 本だけで、iBUS SERVO ポートを使います。送信機で failsafe を設定できる必要があります。この設定は必須です。failsafe の章を参照してください。
- エルロン用の **MG90S サーボ 2 個**。左右の主翼に 1 個ずつです（2 つの独立したサーボで、両翼に 1 個ではありません）。
- エレベーター用の **MG90S サーボ 1 個**。
- ラダー用の **MG90S サーボ 1 個**。同じ軸に降着装置のステアリング用車輪を取り付けています（地上でのかじ取り）。
- **電子スピードコントローラー（ESC）** 60–80 A、5 V の BEC 付き（BEC がサーボと受信機に電力を供給します）。
- **モーター D3548 1100KV**＋**プロペラ 10x5**。
- **LiPo 3S バッテリー**。

オートパイロットのセンサー（すべて I2C です。これらがなくても、機体は手動モードで飛べます）：

- **GY-521**：ジャイロ＋加速度センサー（基板には MPU6050、または私たちのように MPU6500 が載っていることがあります。どちらも対応しています）。
- **BMP581**：気圧センサー（以前の BMP388 もサポートしています）。
- **GY-273**：コンパス（私たちのものは QMC5883P です。QMC5883L にも対応しています）。
- オプションの **OLED 128×64 SSD1306**（I2C）：機上のステータス表示用の画面。

機体：翼幅 1200 mm、翼弦 250 mm、翼型は NACA 4412、PETG による構造（3D プリント）。最初の試作機は、ESP32-C3、モーター D2212 1000KV、40 A の ESC で飛びました。

## ボードの選び方とピン配置

ファームウェアは 4 種類のボードに対応していて、切り替えはビルドパラメーター 1 つです（`pio run -e <環境名>`）。ピン配置はボードごとに異なり、環境ごとにファームウェアに固定されています。配線を自分の判断で変えず、自分のボードの表を見てください。

> **重要：** 現在のメインボードは **STM32H743 (DevEBox H743)** です。起動、USB コンソール、SD カード、iBUS、サーボとモーターはこのボードで確認済みで、センサーはこれから初めて接続します。**esp32-s3 (N16R8)** は以前のメインボードで、ピン配置は全センサーを載せたテストベンチで確認済みです。**esp32-c3** は飛行実績のある古いプロトタイプです。**esp32-dev** のピン配置はチップのドキュメントをもとに選んだもので、**実機では確認していません**。

### STM32H743 (DevEBox H743)：メインボード

`pio run -e stm32h743-devebox`、ボードは MCUDEV DevEBox H743（STM32H743VIT6）です。これがデフォルトのボードです（`default_envs = stm32h743-devebox`）。起動、USB コンソール、SD カードとブラックボックス、iBUS の受信、ARM、送信機からのサーボとモーターの操作はすでに確認済みで、センサーはこれから初めて接続します。

| 用途 | ピン |
|---|---|
| エルロン、左主翼 | PA0 |
| エルロン、右主翼 | PA1 |
| エレベーター | PA2 |
| ESC（スロットル） | PA3 |
| ラダー＋ステアリング車輪 | PD14 |
| 受信機からの iBUS (RX) | PE7 |
| センサーの I2C SDA / SCL（MPU、BMP581、コンパス） | PB11 / PB10 |
| OLED の I2C SDA / SCL（別バス） | PB9 / PB8 |
| GPS：RX（← GPS の TX）/ TX（→ GPS の RX） | PD9 / PD8 |
| MAVLink テレメトリー（無線モデム）：RX / TX | PD0 / PD1 |
| AUX1 / AUX2（サーボ）、ブザー | PD15 / PE9, PE15 |
| センサーの SPI SCK / MISO / MOSI、IMU の CS / 気圧センサーの CS | PB13 / PB14 / PB15, PB12 / PD10 |
| 予備：バッテリー / 電流センサー（ADC。STM32 のファームウェアはまだ読みません） | PC0 / PC1 |

コンソール、ログ、ブラックボックスのダウンロードは、ボードの USB-C（仮想 COM ポート）を通ります。次のピンは使わないでください：PA11/PA12（USB）、PA13/PA14（SWD）、PC8〜PC12 と PD2（µSD スロット）、PE3 と PC5（K1/K2 ボタン）。

テストベンチでのセンサーの接続（モジュールはすべて **3.3 V** で動作し、5 V ではありません）：

| モジュール | ピン |
|---|---|
| MPU-6050 / GY-521（基板には MPU6500 が載っていることもありますが、問題ありません） | VCC–3.3V, GND–GND, SCL–PB10, SDA–PB11, AD0–GND, INT/XDA/XCL は接続しません。単体の MPU-6500 モジュール（10 ピン）も同じで、加えて **NCS–3.3V**（そうしないとチップが SPI に切り替わります）と FSYNC–GND を接続し、EDA/ECL は接続しません。チップを上向きにし、X の矢印を機首に向けます。チップの軸の回転は `Config.h` の `IMU_ROTATION_CW_DEG` で設定します（私たちのクローンでは 90） |
| BMP581 | VCC–3.3V（**3.3V のみ**：多くのモジュールには専用のレギュレーターがありません）, GND–GND, SCL–PB10, SDA–PB11, **SDO–GND**（アドレス 0x46。浮かせたままにしないこと）, **CSB–3.3V**（そうしないとチップが SPI に切り替わります）, INT は接続しません |
| GY-273 (QMC5883P) | VCC–3.3V, GND–GND, SCL–PB10, SDA–PB11, DRDY は接続しません。サーボ、ESC、モーターの配線から離してください |
| OLED 128×64 SSD1306 | VCC–3.3V, GND–GND, SCL–PB8, SDA–PB9 |

サーボには電力を**ボードからではなく**、ESC の BEC（または別の 2 A 以上の 5 V 電源）から供給します。すべての電源のグラウンドは共通にします。USB をつないでいる間は、ESC の赤い線をボードの 5 V につながないでください。

| エレベーター | GPIO6 |

| ラダー＋ステアリング車輪 | GPIO18 |
| 受信機からの iBUS (RX) | GPIO17 |
| センサーの I2C SDA / SCL（MPU、BMP581、コンパス） | GPIO41 / GPIO42 |
| OLED の I2C SDA / SCL（別バス） | GPIO1 / GPIO2 |
| 予備：GPS RX / TX | GPIO39 / GPIO40 |

## 受信機の接続

受信機に必要なのは **iBUS のデータ線 1 本**だけです。FlySky 互換の受信機の多くでは、専用のポートに出ています（「iBUS」と書かれていることが多く、PPM ではない唯一の出力であることもあります）。接続は次のとおりです。

- **受信機の TX（iBUS 出力）** → 上の表にある**ボードの RX ピン**（esp32-c3 では GPIO8、esp32-s3 では GPIO17、esp32-dev では GPIO16）。
- **受信機のグラウンド（GND）** → **ボードの GND**。必須です。グラウンドが共通でないと、プロトコルは動きません。
- **受信機の電源**：別の BEC/レギュレーターから、またはボードの 5 V から取ります。ふだんご自身の機体で受信機にどう給電しているかによります。ファームウェアの特定のピンとは関係ありません。

ファームウェアは受信機に何も送り返さず、受信するだけです。そのため、ボードの TX 線はどこにもつなぐ必要がありません。

ファームウェアでの iBUS ポートの速度は 115200 ボーで、これはプロトコルの標準値です。変更する必要はありません。受信機自身がこの速度を保つからです。

## RC チャンネルの割り当て

この割り当ては、FS-i6 送信機（10 チャンネル、モード 2）と FS-iA6B 受信機を使ったテストベンチで検証しました。

| チャンネル | 送信機の操作部 | 名称 | 動作 |
|---|---|---|---|
| CH1 | 右スティック ←→ | AILERON | ロール：エルロン（2000 = 右） |
| CH2 | 右スティック ↑↓ | ELEVATOR | ピッチ：エレベーター（2000 = スティックを前へ、機首下げ） |
| CH3 | 左スティック ↑↓ | THROTTLE | スロットル。1000 µs = オフ、2000 µs = 最大、制限なし |
| CH4 | 左スティック ←→ | RUDDER | ラダーと降着装置のステアリング車輪（サーボは 1 個） |
| CH5 | SwA | ARM | ARM スイッチ。後述の ARM の章を参照 |
| CH6 | SwB | SWB | 標準ではフラップ：下（手前）で展開、上で格納（後述） |
| CH7 | SwC（3 ポジション） | SWC | 標準ではモード：上が MANUAL、中央が STABILIZE、下が AUTO_TAKEOFF |
| CH8 | SwD | SWD | 標準では RTH（帰還）。オンの間有効 |
| CH9 | VrA | VRA | 標準では安定化の強さ |
| CH10 | VrB | VRB | 標準では巡航速度 |

CH6〜CH10 は、`include/config/Controls.h` に**1 行書くだけで何にでも割り当てられます**。12 種類のモード、10 種類の機能（フラップ、ブレーキ、ペイロード投下、ジオフェンス、ブザーなど）、7 つのダイヤルのどれでも使えます。ボードの電源を入れると、実際の割り当てがシリアルモニターに表示されます。モードと割り当てについては [AUTOPILOT_GUIDE.md](AUTOPILOT_GUIDE.md) にすべて書いてあります。

チャンネルの値はすべて、受信機の標準的なパルス範囲である 1000〜2000 µs で、1500 µs が中央（ニュートラル）です。

### フラップ（フラッペロン）

独立したフラップはなく、エルロンがその役を担います。**SwB を下**（手前）にすると、左右のエルロンが約 1 秒かけてなめらかに同じ角度だけ下がります（`FLAPS_DEPLOYED_US` = 220 µs ≈ サーボホーンの回転 20°。`include/config/Config.h` で変更できます）。これで揚力が増え、離陸と着陸を低い速度で行えます。スティックやオートパイロットによるロールはいつもどおり働きます。エルロンは互いに逆向きに動きますが、今度は下がった位置を中心に動きます。**SwB を上**にすると、同じようになめらかに格納されます。フラップを展開している間は、OLED の 1 行目に `FL` が点灯します。

フラップを展開したままフルロールすると、下がる側のエルロンが上がる側より先に可動範囲の端に達します。これは正常で、エルロンの差動として働きます。

フラップを展開すると、たいてい機首が上がります。スティックを少し前に送る心構えをしておいてください。効果が強い場合は、`FLAPS_DEPLOYED_US` を小さくして調整できます。

## オートパイロットのチャンネル

要点だけ。標準の割り当て（`include/config/Controls.h`）は次のとおりです。

| スイッチ | 動作 |
|---|---|
| **SwC**（CH7） | 上が **MANUAL** ・ 中央が **STABILIZE** ・ 下が **AUTO_TAKEOFF** |
| **SwD**（CH8） | **RTH**：オンの間は帰還 |
| **SwB**（CH6） | フラップ |
| **VrA / VrB**（CH9/10） | 安定化の強さ / 巡航速度 |

- **STABILIZE：「スティックで角度を指定」。** スティックをいっぱいに倒すとロール 45°、ピッチ 25° です。離すと、機体が自分で水平に戻ります。スロットルは自分で操作します。
- **AUTO_TAKEOFF。** ARM の後は、自分でスロットルを半分より上げるまで何も起こりません。その後は、0〜1 秒でスロットルがなめらかに 100% まで上がり、翼は水平。1〜3 秒でピッチ +15°。それ以降は SwC を切り替えるまで +10° です。スロットルは、スティックとプログラムのうち大きいほうになります。
- **RTH。** ARM した地点に向かい、高度 40 m で、その上空を旋回します。**ARM の前に** 3D フィックスした GPS が必要です。

12 種類のモードすべて（ALT_HOLD、ACRO、CRUISE、LOITER、手投げの LAUNCH、AUTO_LAND、SOARING、RESCUE など）と、それぞれに必要なセンサー、スイッチへの割り当て方は [AUTOPILOT_GUIDE.md](AUTOPILOT_GUIDE.md) にあります。ダッシュボードや地上局から選んだモードは、モードのスイッチを操作するまで保持されます。

機体が **ARM されていない**ときも、スタビライズは舵面を動かします。そのため、机の上で、傾けたときにどちらへ反応するかを確認できます。このとき積分器は溜まりません。

角度の符号（OLED とログでの表記と同じ）：**ロール R > 0 は右翼が下、ピッチ P > 0 は機首が上です。**

## ARM と failsafe

### ARM の手順

- **ARM：** スロットル（CH3）を下げた状態で、**SwA（CH5）を下（手前）に**します（FS-i6 では CH5 = 2000、上 = 1000）。Serial に `ArmingManager: ARM` が表示され、OLED に `ARMED` が表示されます。
- **DISARM：** SwA を上（奥）にします。いつでもすぐに効き、モーターは直ちに止まります。
- スロットルが下がっていない状態で SwA を ARM にした場合や、飛行前チェックを通過していない場合は、ARM に**なりません**（理由は Serial に表示されます）。SwA を上に戻し、スロットルを下げてから、もう一度下にしてください。
- SwA がすでに ARM の位置（下）にある状態でボードの電源を入れた場合は、ARM に**なりません**。ファームウェアが、先に SwA が上（OFF）にあることを確認する必要があります。

**ARM は実際にスロットルをロックします。** 機体が ARM されていない間、ESC へのスロットルはスティックの位置にかかわらず強制的に最小値に保たれます。ARM する前に、選択したモードに必要なセンサーが応答することを確認します。たとえば IMU が動作していなければ、MANUAL に切り替えるまで STABILIZE では ARM できません。それでも、ARM した後はいつでもプロペラが回り出すかもしれないつもりで扱ってください。

### Failsafe

通信が途絶えた場合の処理は、ほかのすべてより**絶対的に優先**されます。

- **機体が ARM 済みで、GPS とホームがある場合**：**モーターを使った帰還**（ArduPilot/INAV と同じ）。ホームに向かい、高度 40 m で、通信が回復するまでその上空を旋回します。OLED には `FSRTH` と表示されます。`Config.h` の `FAILSAFE_RTH = false` で無効にできます。
- **機体が ARM 済みで、GPS がない場合**：**滑空**。モーターは停止し、オートパイロットはどのモードでも（MANUAL でも）翼を水平に、機首を水平線よりわずかに下（−3°）に保ち、フラップを格納します。OLED には `RX LOST ... GLIDE` と表示されます。`FAILSAFE_GLIDE_ROLL_DEG` を 10〜20 にすると、機体は緩やかならせんを描いてあなたの上空を旋回します。
- **ARM されていない場合**（地上）、または IMU が応答しない場合：モーターは停止し、エルロン、エレベーター、ラダーはニュートラル（1500 µs）になります。通信が 10 秒途絶えると、「ここにいるよ」ブザーが鳴ります（取り付けてあれば）。

ファームウェアは、通信の途絶を次の 2 つの方法で検出します。

1. **500 ms を超えて iBUS フレームが来ない**：断線、または受信機に電源が来ていません。
2. **スロットルが 950 µs を下回る**：受信機が送信機を見失ったことをこの形で知らせます。**そのためには、送信機で failsafe を設定しておく必要があります**（後述）。通信が途絶えても FS-iA6B はフレームの送信をやめず、スティックの最後の値を繰り返します。設定しないと、ファームウェアは通信の途絶に気づけず、機体は最後のスロットルのまま飛び続けます。

failsafe になっても ARM は解除**されません**。通信が戻ると、機体は再び ARM し直すことなくスティックと選択したモードに従います（空中で、スロットルをゼロにしてスイッチを操作するほうが危険です）。

机の上での確認（プロペラを外して）：ARM → 送信機の電源を切る → OLED に `RX LOST ... GLIDE` と表示され、モーターが止まる。機体を傾けると、舵面が機体を水平に戻そうとするはずです。送信機の電源を入れると `RX ok` となり、操縦がスティックに戻ります。

### FS-i6 送信機での failsafe の設定（必須、1 回だけ）

考え方：通信が途絶えたとき、受信機に約 900 µs のスロットルを出力させます。通常の最小値 1000 より低い値です。

1. `Menu → Functions setup → End points` → チャンネル 3：下側のポイント（左の値）を **120%** にします。保存します（Cancel を長押し）。
2. スロットルを**いちばん下**にします。
3. `Menu → Functions setup → Failsafe` → Channel 3 → **On**。スロットルは下げたままで、Cancel を長押しして保存します。受信機が約 900 µs を記憶します。
4. `End points` に戻り、チャンネル 3 の下側のポイントを **100%** に戻します。保存します。
5. 確認：ARM は不要です。送信機の電源を切ります。約 1 秒後に Serial に `RX=LOST(failsafe пульта)` が表示され、OLED には反転表示の `RX LOST` が出ます。送信機の電源を入れると `RX=OK` になります。

スロットルのトリムは中央に置いてください。トリムを大きく下げると、スロットルが 950 を下回って、ファームウェアが通信の途絶と判断することがあります。

以前ここには **CH8 のブースト**と 40% のスロットル制限がありましたが、削除しました。制限は非力な 3S1P の構成を守るためのもので、新しいバッテリーならフルスロットルでも問題ありません。また、ブーストは、ボードの電源を入れたときに SwD が上になっていると勝手に作動していました。

## ボードへの書き込み

ファームウェアは **PlatformIO**（Arduino フレームワーク、C++）でビルドします。

### PlatformIO のインストール

いちばん簡単なのは、VS Code に拡張機能 **PlatformIO IDE** を入れる方法です（Extensions → 「PlatformIO IDE」を検索 → Install）。CLI も、画面上の便利なビルドボタンも使えるようになります。`pip install platformio` でインストールして、ターミナルで作業することもできます。どちらの方法でも、同じ `pio` コマンドを使います。

### ビルドと書き込み

PlatformIO を入れた VS Code でプロジェクト（リポジトリのフォルダー）を開き、ボードを USB で接続して、ターミナルで自分のボード用のコマンドを実行します。

```bash
# STM32H743 DevEBox（メインボード）
pio run -e stm32h743-devebox -t upload

# esp32-s3 N16R8（以前のメインボード）
pio run -e esp32-s3 -t upload

# esp32-c3（古い試作機）
pio run -e esp32-c3 -t upload

# esp32-dev（標準の ESP32 38 ピン、テストベンチ用）
pio run -e esp32-dev -t upload
```

`-e` をまったく指定しなければ、デフォルトのボード `stm32h743-devebox` がビルドされます。

**STM32 DevEBox：** 最初の書き込みは USB DFU で行います。BT0→3V3 のジャンパーを付け、RST を押してから、上のコマンドを実行します（Windows では「STM32 BOOTLOADER」用の WinUSB ドライバーが必要で、Zadig でインストールします）。その後は、コンソールで `D` キーを押すとボードが自分でブートローダーに再起動するので、ジャンパーは不要になります。コンソールも同じ USB-C を使います。

**esp32-s3：** このボードには USB-C コネクターが 2 つあります。書き込みと Serial は **「COM」** コネクター経由で行います（CH343 ブリッジ。Windows では「USB-Enhanced-SERIAL CH343」と表示されます）。「USB」コネクター（チップ内蔵のネイティブ USB）は作業には不要ですが、挿したままでも問題ありません。

### シリアルモニター

デバッグ出力（チャンネルの状態、ARM、センサー）を、USB 経由でそのままコンソールに表示するには：

```bash
pio device monitor -b 115200
```

速度は必ず 115200 にしてください。そうしないと、文字ではなく読めない文字化けが表示されます。10 秒に 1 回、`SYS` の行が出力されます。ループの周波数（約 500 Hz のはずです）、10 秒間のループ時間の平均と最悪値、iBUS のカウンター、空きメモリです。そのほかは、ログメニューで有効にしたチャンネルから出力されます（後述）。

### コンソール：メニューとログ（シリアルモニター）

キーを押すとすぐに反映され、Enter は不要です（1 行ずつ送信するモニターでは、文字＋Enter）。キャリブレーションと出力のチェックは、機体が ARM されていないときだけ使えます。

| キー | 動作 |
|---|---|
| `h` | **メインメニュー**（テキスト形式で、項目は数字で選びます） |
| `l` | 「ログに何を出力するか」のメニュー |
| スペース | ログの一時停止 / 再開 |
| `s` | すべてのセンサーの詳細な状態（I2C のエラーカウンターを含む） |
| `i` | ジャイロの再キャリブレーションと IMU の飛行前チェック。2 秒間、機体を動かさないでください |
| `o` | **IMU の取り付けキャリブレーション**：基板を機体に取り付けた後に 1 回だけ行います（後述） |
| `m` | コンパスのキャリブレーション：15 秒間、基板または機体をすべての軸まわりに回します。結果はフラッシュに保存され、再起動後も残ります |
| `p` | 出力のチェック：各ピンの実際のパルス |

**チャンネルごとのログ。** データの種類ごとに独自のプレフィックスを持つ行があり、それぞれに独自のモードがあります。**オフ**、**変化時**（値が実際に変わったときだけ行が出ます。スティックの揺れやセンサーのノイズは数えません）、**常時**（0.2 / 0.5 / 1 / 2 秒ごと。周期は同じメニューで設定します）。

| チャンネル | 表示内容 | 標準 |
|---|---|---|
| `STAT` | 通信、ARM、モード、フラップ、IMU・気圧センサーが正常か | 変化時 |
| `RC` | 送信機のチャンネル、µs | オフ |
| `OUT` | 舵面と ESC への出力、µs | オフ |
| `ATT` | ロール、ピッチ、針路 | オフ |
| `AP` | オートパイロット：目標と補正 | オフ |
| `ALT` | 高度、垂直速度、ALT_HOLD の目標 | オフ |
| `MAG` | コンパスによる方位 | オフ |
| `GPS` | フィックス、衛星、座標、速度 | オフ |
| `IMU` | ジャイロと加速度センサー | オフ |
| `SYS` | ループの周波数と時間、メモリ（10 秒ごと） | オン |

メニューを開いている間はログが止まり、メニューが流れてしまうのを防ぎます。メニューを閉じると、有効なチャンネルがすべて改めて出力されます。選択はメニューを閉じるときにフラッシュに保存され、再起動後も残ります。ARM 中は即座に有効になりますが、書き込みは DISARM の後に行われます。フラッシュへの書き込みは、飛行ループを約 0.4 秒止めるためです。

### IMU の取り付け：向きは自由、キャリブレーションは 1 回

IMU を載せた基板は、**都合のよい向きで**機体に取り付けられます。どんな角度でも、横向きでも、上下逆さまでも構いません。基板のどちらが機首で、どちらが上かは、ファームウェアが自分で判断します。これは取り付けの後に**1 回だけ**行います（基板を付け替えたときは、もう一度行います）。

1. 機体を机の上に置きます。送信機は不要で、モーターは ARM しません。シリアルモニターで `o` を押します。
2. **ステップ 1**：機体を水平飛行のときと同じように水平に置きます（尾輪の機体は、尾部の下に何かを挟んでください）。約 3 秒間、触らないでください。
3. **ステップ 2**：**機首**を 30〜60° 持ち上げ、翼は水平のまま、約 1 秒間じっと保ちます。
4. **ステップ 3**：機首を戻し、**右翼**を 30〜60° 下げて、約 1 秒間保ちます。

各ステップは自動的にカウントされます（ログには「засчитано」、つまり「カウント済み」と出ます）。最後に結果（「нос = +Y чипа, верх = −Z чипа」、つまり「機首＝チップの +Y、上＝チップの −Z」）と「установка сохранена」（「取り付け情報を保存しました」）が表示されます。間違えた場合（機首を持ち上げずに下げた、右翼ではなく左翼を下げた）は、理由とともにキャリブレーションが拒否されるので、もう一度 `o` を押してください。結果はフラッシュに保存され、再起動後も残ります。確認：機首を上げる → OLED の P がプラスになる、右翼を下げる → R がプラスになる。

取り付けのキャリブレーションがない間は、従来の方法が使われます。基板はチップを上向きにして置く必要があり、回転は `Config.h` の `IMU_ROTATION_CW_DEG` で指定します。

### 電源投入時の飛行前チェック

電源を入れるたびに、IMU は約 2 秒かけてジャイロをキャリブレーションし、同時に自己チェックも行います。

- **機体が静止していること**：そのとき手に持っていたり動かしていたりすると、ジャイロのオフセットが正しくなくなります。
- 加速度センサーが静止時に 1g を示すこと。
- **「上」が取り付けキャリブレーションと一致していること**：基板を付け替えたり裏返したりした場合は、すぐに分かります（尾輪で立っている機体や斜面に置いた機体は問題ありません。許容範囲は 45° です）。

**機体を静止させたまま電源を入れてください**。取り付けがキャリブレーション済みなら、水平である必要はありません（そうでなければ、電源投入時の姿勢が水平線になります）。結果はログに出ます。`предполётная проверка пройдена`（「飛行前チェックに合格」）または `ПРЕДПОЛЁТНАЯ ПРОВЕРКА НЕ ПРОЙДЕНА — <причина>`（「飛行前チェックに不合格」。続けて理由）です。不合格の場合、**STABILIZE と AUTO_TAKEOFF での ARM は禁止され**（試みたときに理由が表示されます）、オートパイロットはどのモードでも、通信途絶時の滑空も含めて補正を一切行いません。角度が間違っていると、逆向きに舵を切ってしまうからです。MANUAL では ARM できます。直し方：機体を静止させて置き、バッテリーをつなぎ直す（または `i`）。基板を付け替えた場合は `o` です。

### OLED 画面

OLED を接続している場合（GPIO1/GPIO2）、1 秒に 5 回、次の内容を表示します。

```
RX ok disarm STAB        <- 通信 / ARM / モード（通信が途絶えると行が反転表示になります）
R  +1.2 P  -0.4          <- ロール / ピッチ、°
Alt +0.3 Vz +0.1         <- 電源投入地点からの高度、m / 垂直速度、m/s
Hdg 123  Thr 1000        <- コンパスの方位 / ESC へのスロットル、µs
L1500 R1500 E1500        <- エルロンとエレベーターの PWM、µs
Loop 500Hz max 1100us    <- 周波数とループ時間の最悪値
```

## 現場での Web ダッシュボード

ボード自身が Wi-Fi アクセスポイントを立ち上げます。自宅のルーターもインターネットも不要で、すべて現場でスマートフォンからそのまま使えます。

**接続方法：**

1. スマートフォンまたはノートパソコンで、Wi-Fi ネットワークの一覧を開きます。
2. ネットワーク **`OpenPlane-Debug`** に接続します。パスワードは **`12345678`** です。
3. ブラウザーでアドレス **`http://192.168.4.1`** を開きます。

アプリをインストールする必要はありません。ごく普通の Web ページです。

**現場でスマートフォンから、プログラミングなしでできること：**

- **全 10 本の RC チャンネルのライブバー**を確認できます。サーボをつなぐ前でも、送信機と受信機がスティックの動きどおりの値を実際に送っているかを確かめられて便利です。
- 各出力（左右のエルロン、エレベーター、ESC）の状態を確認できます。チャンネルがソフトウェア上で接続されているかどうかが分かります。
- センサー（IMU、気圧センサー）を実装している場合、応答しているかどうかを確認できます。実際のデータ（ロール / ピッチ / 高度）か、センサーが物理的に存在しない、または応答しないという明確な表示のどちらかが、偽りなく表示されます。
- ページ上のボタンで**オートパイロットのモードを切り替え**られます（手動 / スタビライズ / 自動離陸 / 高度保持）。送信機は不要です。
- ページ上のフォームで **PID コントローラーの係数を調整**できます（ロールとピッチ）。ファームウェアを書き直さずに、スタビライズを少しずつ詰めていくのに役立ちます。

このアクセスポイントの到達距離は、実際には数十メートルです。ESP32 のごく普通の Wi-Fi であり、長距離テレメトリーではありません。机の上、テストベンチ、現場のそばで調整するための道具であり、離れた場所を飛行中の機体を操縦するためのものではありません。

## ブラックボックス

ESP32-S3 のファームウェアは、すべてのフライトを自分でフラッシュに書き込みます。センサーが見たものすべて、スティックの動き、サーボの動き先、オートパイロットの判断です。何もする必要はありません。

- 機体が ARM され、スロットルが上げられた時点から**記録します**（その前の 10 秒分も含みます）。
- DISARM の 10 秒後に**止まります**。または、ARM されたままの機体がモーターを止めた状態で 30 秒間じっと動かない場合も止まります（着陸または墜落して、DISARM を忘れた場合）。
- 通信途絶、モーターのゼロ、滑空では、記録は**止まりません**。

電源を入れると、シリアルモニターに 1 回のフライトに使える空き容量が表示されます（コンソールの出力はロシア語です。下の行は「ARM とスロットルを待機中 | 前方の消去済み 12.9 MB（約 11 分）/ 全体 13.9 MB | フライト数 1」という意味です）。

```
BlackBox: ждёт ARM и газ | стёрто впереди 12.9 МБ (≈11 мин) из 13.9 МБ | полётов 1
```

**フライトの後**に USB（COM コネクター）をつなぎ、シリアルモニターを閉じて、フライトのデータをダウンロードします。

```bash
python tools/blackbox.py download
```

フライトの記録は、解析結果とともに `blackbox/` フォルダーに保存されます。`summary.txt`（概要とイベント）、`events.txt`、センサーごとの CSV 表です。ブラックボックスは空き容量が必要になると古いフライトを自分で消すので、**飛行のたびにダウンロードしてください**。コンソールのメニューは `k` キーです。詳細はすべて [BLACKBOX.md](BLACKBOX.md) にあります。

**STM32H743 ボードでは**、ブラックボックスは SD カードに書き込みます。カードは FAT32 でフォーマットし、PC で 1 回だけ準備します（`python tools/blackbox.py sd-prepare E:`）。フライトの後は、同じ `download` コマンドで USB 経由でダウンロードできます。カードを抜いて、そのままファイルを解析することもできます：`python tools/blackbox.py ring E:/BLACKBOX.BIN`。

## 飛行前チェックリストと安全

この章は、事故が起きてからではなく、初めて電源を入れる**前に**最後まで読んでください。

### テストベンチでの試験の前に必ず行うこと

- [ ] **プロペラを物理的に取り外してある**（チャンネル、ARM、ダッシュボードの確認、PID の調整、新しいピン配置で初めてボードに電源を入れるとき）。ESC は試験のどの段階でもモーターを急に動かすことがあります。これは仮定のリスクではなく、初回の電源投入時の通常の挙動です。
- [ ] LiPo バッテリーは、膨らみや損傷がないか点検し、適切な LiPo 用充電器で充電してあり、不燃性の面の上で保管・充電している。
- [ ] 送信機の電源が入っており、バッテリーを ESC につなぐ**前に**、ダッシュボード（`http://192.168.4.1`）でチャンネルを確認した。

### 飛行前

- [ ] 開けた場所で、周囲に人も建物もない。その半径は、翼幅 1200 mm の機体を手動操縦しているときにサーボや翼が異常な動きをしても安全なだけの広さにしてください（下の「試作機体の現状」の章を参照。モーターの取り付け部と主翼は、まだカーボンで補強されていません）。
- [ ] 3 つの舵面がすべて正しい向きに動く。前回の記憶に頼らず、毎回の飛行前に机の上で確認してください。
  - 右スティックを右へ → **右エルロンが上、左エルロンが下**。
  - 右スティックを手前へ → **エレベーターが上**。
  - 左スティックを右へ → **ラダーとステアリング車輪が右**。
  - SwB（フラップ）を下へ → **両方のエルロンがゆっくり下がり**、そのうえでスティックによるロールでは、両方のエルロンが互いに逆向きに開く。
  - STABILIZE で機体の右翼を下げて傾ける → **右エルロンが下、左エルロンが上**（舵面が機体を水平に戻します）。機首を下げる → **エレベーターが上**。何かがおかしい場合は、送信機でリバースにするのではなく、`include/config/Config.h` の対応する `*_REVERSED`（「サーボの向き」のセクション）を変更してください。送信機側で変えると、スティックとオートパイロットの向きが食い違います。
- [ ] 電源を入れたとき機体は静止しており、ログやダッシュボードに `ПРЕДПОЛЁТНАЯ ПРОВЕРКА НЕ ПРОЙДЕНА` が出ていない。機体を手で傾けると、OLED の P と R が正しい向きに変わる。
- [ ] 送信機で failsafe を設定し、動作を確認してある。送信機の電源を切る → OLED または Serial に `RX LOST`（failsafe の章を参照）。
- [ ] 送信機の通信距離を確認してあり、送信機のバッテリーは充電済み。
- [ ] 電源を入れたとき、ログに `BlackBox: ... стёрто впереди N МБ (≈M мин)` と出ており、1 回のフライトに十分な空きがある。前回のフライトは、必要であればダウンロード済み（`python tools/blackbox.py download`）。
- [ ] LiPo が ESC につながっている間は、常にプロペラから手と顔を離しておく。ARM 後は、追加の警告なしに、スロットルがスティックにすぐ反応します。DISARM は SwA を上へ。
- [ ] 信号喪失時の failsafe だけに頼らず、電源を物理的にすばやく切れること（LiPo のコネクターに手が届くこと）を確認する。

### LiPo の安全に関する一般事項

- 充電中の LiPo から目を離さないでください。
- プロペラの回転面のそばに立ったまま、LiPo を ESC に接続したり外したりしないでください。
- LiPo は、保護バッグまたは保護ケースに入れて運搬・保管してください。

## トラブルシューティング

**「受信機の信号がない」 / RX は正常に見えるが、ダッシュボードのチャンネルが動かない**
受信機のデータ線が、お使いのボードの表にある iBUS の RX ピン（GPIO8/GPIO17/GPIO16）にちょうど接続されていて、GND や電源線と取り違えていないこと、そして受信機とボードの GND がつながっていることを確認してください。ピン配置が合っていて配線も無事なのに信号がない場合は、受信機が送信機とそもそもバインド（bind）されているか、受信機の出力が PPM/SBUS ではなく iBUS に設定されているかを確認してください。

**センサー（IMU、気圧センサー、コンパス）が「応答なし」/ NO_RESPONSE と表示される**
ファームウェアは、ゼロを出力する代わりに、センサーが応答しないことを正直に報告します。次を確認してください。（1）モジュールの電源：3.3V とボードの GND。（2）SDA/SCL：お使いのボードの I2C ピンにつながっているか。（3）ライン上のアドレス：MPU 0x68（AD0 を GND に）、BMP581 0x46（SDO を GND に、CSB を 3.3V に。SDO を 3.3V にすると 0x47）、BMP388 0x76（SDO を GND に、**CSB を 3.3V に**つなぎます。そうしないとチップは SPI モードになります）、QMC5883P 0x2C、QMC5883L 0x0D。センサーが応答したりしなかったりする（あるいは別のアドレスで応答する）場合は、ブレッドボードの接触不良です。VCC/GND/SDA/SCL をしっかり押し込み、各モジュールはボードの 3.3V/GND から直接給電するのが確実です。コンソールの `s` コマンドは、センサーごとの I2C エラーカウンターを表示します。

**OLED の角度が入れ替わっている（機首を上げると P ではなく R が変わる）、または符号が逆**
IMU の取り付けキャリブレーション（`o`、「IMU の取り付け」を参照）を行ってください。チップがモジュールにどう半田付けされているかも、モジュールが機体にどう置かれているかも関係ありません。キャリブレーションがない場合：GY-521 の互換品では、チップが印刷された矢印に対して回転した向きで半田付けされていることがあります。`Config.h` の `IMU_ROTATION_CW_DEG`（0/90/180/270）で軸を回してください。確認：機首を上げる → P がプラス、右翼を下げる → R がプラス。

**ARM が拒否された：「IMU: ...」**
IMU の飛行前チェックに合格しませんでした（「電源投入時の飛行前チェック」を参照）。電源投入時に機体が動かされた：静止させて置き、バッテリーをつなぎ直してください。「上」がキャリブレーションと一致しない：基板が付け替えられているので、`o` を行ってください。「基板がチップを上にして置かれていない」：取り付けがキャリブレーションされていないので、`o` を行ってください。

**サーボまたは ESC が別のスティックに反応する / 反応しない**
コンソールの `p` コマンドは、各出力（GPIO4〜7）の実際のパルスを測定し、期待値と比較します。すべて「OK」なのにサーボが動かないなら、問題はボードの先にあります。（1）サーボに電源が来ていない（BEC/5V、GND の共通化）。（2）信号線が違うピンにつながっている。（3）機構が固着している。「НЕ СОВПАДАЕТ」（「不一致」）と出た場合は、問題はファームウェアか周辺機器にあります。開発者に知らせてください。

**OLED やダッシュボードのスロットルはスティックに反応するのに、モーターがまったく回らない**
LiPo が ESC につながっていること、そして機体が本当に ARM されていることを確認してください。ARM の前は ESC へのスロットルが強制的に最小値に保たれており、これは故障ではありません。電源投入時に最小ではないスロットルを検出した ESC は、鳴り続けて ARM されないことがあります。スロットルを下げた状態でバッテリーをつなぎ直してください。SwA を下げても `ArmingManager: ARM` が出ない場合は、Serial を見てください。ファームウェアが理由を表示します（スロットルが下がっていない、センサーが応答しない、CH7 で現在選ばれているモードが必要とするセンサーが応答しない、など）。SwA を上に戻し、原因を取り除いて、もう一度下げてください。

**加速時にモーターが止まる、またはギクシャクする**
ESC を実験用電源から給電している場合は、電源の電流制限に引っかかっています。プロペラがなくても、モーターは一瞬で数アンペアを引き込み、電圧が落ちて ESC が再起動します。電流制限を上げるか、LiPo を使ってください。このような再起動で出るノイズは、ボードの USB ブリッジをハングさせることがあります（「COM」ポートが開かなくなる）。その場合はケーブルをつなぎ直してください。

**書き込み後にボードが反応しない / アクセスポイント `OpenPlane-Debug` が現れない**
書き込み（`pio run -e <お使いのボード> -t upload`）がエラーなく終わったこと、そして手元にあるボードに対応する環境を書き込んだことを確認してください（esp32-c3 は、esp32-s3 や esp32-dev とピンだけでなくチップも異なります。別のチップ向けのファームウェアはボードに入らないか、正しく入りません）。ボードを再起動した直後に、シリアルモニターの出力（`pio device monitor -b 115200`）を確認してください。ボードが setup() のどの段階にいるかが表示されます。

## 試作機体の現状

期待を正直なものにしておくために：

- 最初の試作機は**すでに飛行しました**。その結果、問題が判明しています。**モーターの取り付け部の強度不足**と**主翼の強度不足**で、主翼にはカーボンによる補強が必要です。サーボの追加調整も必要です。ご自身の飛行を計画するときは、この点を考慮してください。これは抽象的な但し書きではなく、この試作機で実際に起きた故障です。
- **esp32-s3 のテストベンチは、すべてのセンサーを載せて組んであります**（MPU6500 を載せた GY-521、I2C 接続の BMP388、QMC5883P を載せた GY-273、OLED）。すべて応答し、ループは 500 Hz で回っています。オートパイロットの各モードは机の上で確認しましたが、**まだ飛行では試していません**。
- 既定の気圧センサーは BMP581 になりました（ベンチの BMP388 は実機で確認済み、BMP581 はまだ実機で試していません）。高度は電源投入地点を基準にした相対値です。海抜の絶対高度は標準大気から求めており、天候による補正はありません。
- コンパス QMC5883P は、組み上がった機体でのキャリブレーション（コンソールの `m`）が必要です。モーターや配線の近くでは、ブレッドボード上とはオフセットが異なります。針路には傾き補正がまだなく、どのモードでも使われていません。
