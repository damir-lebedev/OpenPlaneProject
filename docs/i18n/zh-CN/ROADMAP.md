## 1. 现状——如实说明

OpenPlaneProject 目前是一架飞过、但尚不成熟的滑翔机原型，运行自行编写的 ESP32 固件，它既不是成品，也不是自主无人机。硬件方面：翼展 1200 mm，翼弦 250 mm，NACA 4412 翼型，PETG 结构（3D 打印），MG90S 舵机（每个副翼单独一个），3S LiPo 供电。第一架原型机（ESP32-C3、D2212 1000KV 电机、40A 电调）已经在手动控制下飞行过，飞行之后暴露出一些具体问题：电机和机翼的固定强度不足（需要用碳纤维加固），以及舵机需要调校。

当前这一版已改用 ESP32-S3（N16R8），搭配 D3548 1100KV 电机和 60–80A 电调，自动驾驶仪所需的全部传感器都已在台架上接好：IMU（MPU6500）、BMP388 气压计、QMC5883P 电子罗盘，另有 OLED 状态屏。已实测验证：通过 iBUS 的手动遥控，混控副翼、升降舵、方向舵（含可转向的前轮）和襟翼（襟副翼）；用单独的开关 ARM；遥控器关闭时的失控保护（failsafe）；500 Hz 的控制循环；通过 Wi-Fi 的实时网页仪表盘。放在桌面上时，增稳会朝正确的方向响应倾斜。

此后固件新增了 12 种自动驾驶仪模式（增稳、定高、巡航、按 GPS 绕圈和返航、手抛起飞、自动降落、在热气流中翱翔、“救援”）、地理围栏、信号丢失时返航、载荷投放、由两个气压计组成的皮托管、对新传感器（LSM6DSV、ICM-45686、QMC6309、SPL06、BMP581）的支持，以及面向 STM32H743、带 MAVLink 遥测（供 QGroundControl 使用）的完整固件。所有这些都经过了 387 个自动化测试和闭环飞行仿真的检验（整套固件驾驶一个飞机模型），但**尚未在空中试飞过**。换句话说：到目前为止飞过的只有手动控制；自动驾驶仪已经写好，用一切无需飞行就能用的手段检验过，正等待飞行测试。

## 2. 为什么这很重要

低门槛的自主小型航空，能解决这样一些任务：决定成败的不是最大载重或航程，而是反应速度和低使用成本：

- **向偏远地区和灾后地区运送药品和血液**——道路被冲毁、没有基础设施、自然灾害或冲突后的破坏。这里起决定作用的不是载重（包裹很小），而是反应时间：以分钟和小时计，而不是开车或步行要用一天。
- **搜索与救援行动**——在地面小组到达之前，向受困者精准投放装备、急救包、通信设备和浮具，适用于直升机成本过高、或因天气和地形而无法出动的区域。
- **精准农业**——监测作物，以及在需要的地方定点喷洒/施用药剂；这类任务的封闭式无人机平台动辄数千美元起步，对中小农场来说不划算。

在这三类场景里，经济账是一样的：差别在于“有解决方案，但昂贵且封闭”和“实际上没有解决方案，因为太贵”之间——廉价的开放平台瞄准的正是这块空白。这是在描述应用领域和市场问题，并不是声称 OpenPlaneProject 已经能够运送货物——在现阶段，这只是一个关于目标、以及这个目标为什么值得追求的陈述。

## 3. 投资论点：为什么开放的 ESP32 架构是一种不对称优势

用于配送/监测的商业自主无人机平台，通常建立在封闭的飞控和封闭的软件之上，每架售价从数百到数千美元不等，并且运营机队还要缴纳授权费或签订服务合同。OpenPlaneProject 出发的假设则不同：

- **低成本的基础。** 一块 ESP32 模块的价格约为 5–15 美元，周边器件（MG90S 舵机、电调、iBUS 接收机）都是标准的业余级元件。这比进入封闭商业平台的门槛低一个数量级，对预算受限环境中的试点部署至关重要（非营利组织、小规模农业、地区救援机构）。
- **开放的代码改变了信任的经济学。** 部署机队用于医疗配送的组织，可以审计安全逻辑（failsafe、ARM），并根据自己的传感器和规程调整固件，而不必依赖单一供应商及其路线图。
- **这套架构在今天就是为扩展而设计的，而不只是为当前这架滑翔机。** 这不是宣言，而是代码结构的直接结果：
  - 新增传感器时，只需写一个实现现有接口 `Sensor` → `ImuSensor`/`BarometerSensor`（`include/sensors/SensorInterface.h`）的类，无需改动核心。IMU（MPU6050/MPU6500、ICM-42688）、气压计（BMP388、BME280）、电子罗盘（QMC5883P/L）和 GPS（u-blox M10）的驱动就是这样做出来的——全部通过总线寄存器直接编写（接口为 `II2CBus`/`ISpiBus`/`IUartPort`），不依赖第三方库，也就是说没有对某个厂商 SDK 的隐藏依赖。
  - 新增开发板，只需在 `include/config/Config.h` 中加一个 `#elif` 块，再在 `platformio.ini` 中加一个 `[env:...]` 块——切换开发板如今已对四个目标可用（见下表），这并非假设中的可能性。
  - `Autopilot.h` 已经把 `ImuSensor*`/`BarometerSensor*` 作为参数接收（可以是 `nullptr`）——也就是说，自动驾驶仪与硬件之间的契约本来就预期传感器组成会变化（下一步是把 GPS 作为同一模式的又一个类，见阶段 3）。
  - `WebDebugServer.h` 已经提供统一的聚合 JSON（`GET /api/status`），并接收命令（`POST /api/setmode`、`/api/setpid`）——也就是说，“飞机提供遥测并接收命令”的协议已经存在，地面站应当从它生长出来，而不是从零编写。

不对称优势在于：这个平台的入门门槛（资金、适配新任务所需的时间）比封闭同类低一个数量级，同时通往自主飞行的道路不需要重写核心——只需要在现有接口之上添加新的类。这是一个开放的工程平台，而不是现成的商业产品——因此，对投资人/合作伙伴的论点不是“买现成的方案”，而是“在地基已经验证、下一步在技术上清晰的阶段加入”。

## 4. 当前的架构——后续各阶段的基础

### 4.1 支持的开发板

选择开发板只是一个 PlatformIO 构建选项，切换开发板不需要改动逻辑（`include/config/Config.h` + `platformio.ini`）：

| 环境（`pio run -e ...`） | 开发板 | 状态 | aileron L / R | elevator | esc | ibus_rx | i2c sda / scl |
|---|---|---|---|---|---|---|---|
| `esp32-s3`（默认） | ESP32-S3 N16R8（DevKitC-1） | **主力板，已在台架上连同全部传感器验证** | GPIO4 / GPIO5 | GPIO6 | GPIO7 | GPIO17 | GPIO41 / GPIO42 |
| `esp32-c3` | ESP32-C3 SuperMini | 第一架原型机，已在手动控制下飞行 | GPIO5 / GPIO4 | GPIO6 | GPIO7 | GPIO8 | GPIO1 / GPIO3 |
| `esp32-dev` | 经典 ESP32 38 针版 | 用于台架，**尚未在硬件上验证**（整套固件在测试中运行） | GPIO13 / GPIO14 | GPIO27 | GPIO26 | GPIO16 | GPIO21 / GPIO22 |
| `stm32h743` | STM32H743VIT6（WeAct Mini） | 完整固件 + MAVLink，**目前还没有开发板**（整套固件在电脑上的测试中运行） | PA0 / PA1 | PA2 | PA3 | PE7 | PB11 / PB10 |

烧录固件：`pio run -t upload`。串口监视：`pio device monitor`（115200）。

### 4.2 RC 通道图（FS-i6 + FS-iA6B，iBUS，10 个通道，1000–2000 µs）

| 通道 | 名称 | 默认用途 |
|---|---|---|
| CH1–CH4 | 摇杆 | 横滚、俯仰、油门、方向舵 |
| CH5 | ARM | 拨杆 SwA：油门在底时 ARM，DISARM 立即生效 |
| CH6 | SWB | 襟翼 |
| CH7 | SWC | 模式：MANUAL / STABILIZE / AUTO_TAKEOFF |
| CH8 | SWD | RTH——返航 |
| CH9 | VRA | 增稳强度 |
| CH10 | VRB | 巡航速度 |

CH6–CH10 在 `include/config/Controls.h` 中用一行即可分配：12 种模式中的任意一种、10 种功能（襟翼、减速板、载荷投放、地理围栏……）和 7 个旋钮——见 [AUTOPILOT_GUIDE.md](AUTOPILOT_GUIDE.md)。

### 4.3 控制流程（`FlightController::update()`）

只有一个调度者，顺序固定，循环为 500 Hz、周期固定：接收 iBUS → 飞手油门 → 来自 CH7 的模式 → **读取传感器并计算自动驾驶仪（始终进行，即使没有信号）** → **以绝对优先级检查信号丢失**（在空中——有 GPS 时开着电机按 GPS 返航，没有 GPS 时机翼保持水平滑翔；在地面——舵面回中）→ ARM → 摇杆指令 + 自动驾驶仪的修正，统一采用航空符号约定 → 带舵机反向的混控器 → 模式的油门 → 未 ARM 时锁定油门 → 写入舵机/电调。正是这种顺序上的纪律（安全第一，其次是手动控制，再其次才是作为上层附加的自动驾驶仪），使得可以放心地往里加入越来越自主的行为，而不必重写基础循环。Wi-Fi、仪表盘和屏幕运行在第二个核心上，不会拖慢控制。

### 4.4 网页仪表盘——地面站的雏形

`WebDebugServer.h` 现在就能建立接入点（SSID `OpenPlane-Debug`，IP `192.168.4.1`），并收发 JSON：

| 方法与路径 | 作用 |
|---|---|
| `GET /api/status` | 一个聚合的 JSON：RC（10 个通道）、armed/failsafe、7 路输出（`us`、`attached`）、IMU、气压计、电子罗盘、GPS、皮托管（每个都有 `attached`/`available` + 数据）、自动驾驶仪（模式、修正、PID、导航、已启用的功能） |
| `POST /api/setmode` | `{mode: 0-11}`——切换自动驾驶仪模式 |
| `POST /api/setpid` | `{kpRoll, kiRoll, kdRoll, kpPitch, kiPitch, kdPitch}`——任意字段均可省略 |
| `GET /` | HTML 仪表盘：10 个通道的实时条形图、每路输出/每个传感器的状态、模式按钮、PID 表单 |

JSON 中的 `attached`/`available` 字段始终存在——仪表盘会如实地区分“配置中没有”和“配置中有、但没有响应”，而不是对缺失的传感器保持沉默。这与贯穿整份文档的诚实原则一致：不把希望当成现实。

## 5. 分阶段的技术路线图

下面是八个阶段，每个阶段都被描述为在现有类之上的下一个合乎逻辑的步骤，没有编造的日期和金额。

### 阶段 1 — 手动控制与安全的基础 [已完成]

**目标**：可靠、可预测、调试透明的遥控滑翔机。**技术上已有的内容**：`IBusReceiver.h` 中带信号丢失识别的 iBUS 解析，混控器 `ControlMixer.h`（摇杆 → 横滚/俯仰/襟翼指令 → 带舵机反向的 PWM，对 UART/PWM 一无所知），`ThrottleManager.h`，`ArmingManager.h`（用单独的开关、油门在底时 ARM，DISARM 立即生效），`FlightController.h` 中拥有绝对优先级的 failsafe，输出到 Serial（`DebugLogger.h`），网页仪表盘（`WebDebugServer.h`）和 OLED 屏（`OledDisplay.h`）。**为什么这是其余一切的基础**：这是唯一一层必须始终工作的层，哪怕其余各阶段都还没实现，或它们的传感器已被断开——正因如此，failsafe 和 ARM 最先写成，并在硬件上验证过（包括 FS-iA6B 接收机在遥控器关闭时的实际行为）。

### 阶段 2 — IMU + 气压计 → 自动驾驶仪 [已编写，并经测试和仿真验证，等待飞行测试]

**目标**：第一个自主飞行模式——地平线增稳、自动起飞、定高。**技术上已有的内容**：`imu/MPU6050_Sensor.h`（MPU6050 和 MPU6500，直接操作寄存器，按电路板的安装方式旋转轴，航空符号约定，`ImuSensorBase` 中的互补滤波器），`baro/BMP388_Sensor.h`（I2C 或 SPI，完整的 Bosch 补偿，依据数据就绪标志读取，经过滤波的垂直速度），带 `PidController` 的 `Autopilot.h`（D 项取自陀螺仪，积分器只在 ARM 之后累积）和十二种模式（从 MANUAL 到 SOARING 和 RESCUE），可按 `Controls.h` 的表用拨杆切换，也可从网页仪表盘和 QGroundControl 切换，另有 failsafe（返航或滑翔）。每一种模式都在整套固件驾驶飞机模型的闭环仿真中飞行过（`test/native/test_sim`）。在装有 ESP32-S3 的台架上，所有传感器都有响应，符号方向已实测验证：倾斜 → 舵面朝改平的方向修正。**要结束这个阶段还需要**：把电子设备装进滑翔机，在组装好的机体上检查舵面方向，并进行首次飞行测试——从安全高度上的 STABILIZE 开始。

### 阶段 2.5 — 基于真实飞机的反馈 [雏形，已在仿真中验证]

**目标**：让自动驾驶仪不依赖针对某一速度整定出来的系数，而是依赖真实飞机此刻对舵面的响应。阶段 2 的 PID “按公式”偏转舵面，并不检查结果；速度小时它修正不足，速度大时修正过头。**技术上已有的内容**（`include/autopilot/feedback/`，**尚未接入**固件）：飞行中对舵面效率的估计（递推最小二乘，按速度换算，∝ V²），“角度 → 转动速率 → 舵面”的控制器，带补偿修正（“舵面没有转到位——再多转一点”），防止速度丢失和失速的保护（油门、机头向下、机翼水平），从跑道或手抛起飞，以及按传感器分阶段进行的降落。所有这些都在开发板本身上经过飞机闭环仿真的检验（`pio test -e esp32-s3 -f test_feedback`，10 个场景）——包括副翼接反、颠簸、小油门下机头上扬、起飞和降落。**要结束这个阶段还需要**：在阶段 2 的首批飞行之后——“影子模式”（反馈只把它本会做的动作写入日志），然后逐个轴接入，再加上空速传感器（皮托管）和用于触地前拉平的测距仪。详见 [`DEVELOPER_GUIDE.md`](DEVELOPER_GUIDE.md) 中的“反馈”一节。

### 阶段 3 — GPS 与电子罗盘 [已在固件中，经仿真验证]

**状态（已更新）：导航已经可用**——基于 GPS/电子罗盘/陀螺仪并带滞回的航向、ARM 时设定返航点、CRUISE、LOITER（收敛到圆周的向量场）、RTH、地理围栏；已通过闭环仿真验证。以下是该阶段的原始记录。GPS（u-blox M10，`sensors/gps/UbloxM10_Gps.h`，UBX-NAV-PVT 协议）和磁力计（“GY-273”板的两种型号：QMC5883P——`sensors/mag/QMC5883P_Sensor.h`，装在当前台架上，已实测验证；QMC5883L——`sensors/mag/QMC5883L_Sensor.h`）都是作为实现 `GpsSensor`/`MagnetometerSensor` 接口（`include/sensors/SensorInterface.h`）的新类加入的，原则与 IMU 和气压计相同——`Autopilot.h` 和 `FlightController.h` 没有重写，只是以同样的方式（构造函数中的可空指针）多接入了两个数据源。顺带出现了 HAL 层（`include/hal/`），传感器通过它访问总线——I2C/SPI/UART 不再直接绑定到 ESP32 特有的 `Wire`/`SPI`/`HardwareSerial`。

目前，GPS/电子罗盘的数据可通过 `Autopilot::getGpsSensor()`/`getMagnetometerSensor()` 以及 `GET /api/status` 获取，另外启动时会根据电子罗盘一次性设定初始 yaw——**但不参与控制**。要结束该阶段尚未解决的问题：把 GPS 模块接到 ESP32-S3（UART2 的引脚已预留）、在组装好的机体上校准电子罗盘，并在航向中加入倾斜补偿。在 ESP32-C3 上无法使用完整的 GPS——没有足够的 GPIO 用于 TX（见 `DEVELOPER_GUIDE.md` 中的引脚分配）。

### 阶段 4 — 沿航路点飞行（waypoint navigation）[下一步]

**状态**：基础功能已经就绪——`Guidance::rollForCourse`、绕点转圈、返回某点（RTH）、用于上传任务的 MAVLink 通道（目前收到任务请求时，飞机会如实回答“0 个点”）。尚缺：航线存储、航点之间的切换、MAVLink 的 MISSION_* 协议。

**目标**：飞机沿给定的一组坐标飞行，航线的每一段都无需操作员参与。**这与架构的契合方式**：这是 `Autopilot.h` 中的一个新 `AutopilotMode`，与已有的 MANUAL/STABILIZE/AUTO_TAKEOFF/ALT_HOLD 并列——也就是说，模式切换的机制（通过 RC 槽位和 `POST /api/setmode`）不变，只是新增第五种模式，它的航向和距离取自 GPS（阶段 3），而不是通过 RC 手动输入。**技术上还需要**：计算指向某点的航向的算法，以及在航线各点之间切换的逻辑，外加把航线本身上传到飞机的方法（自然的候选是扩展已经用来控制模式和 PID 的同一套 HTTP API）。

### 阶段 5 — 远距离遥测 [已在 STM32 固件中完成]

**状态**：在 STM32H743 上——通过无线电数传实现 MAVLink 2（SiK，MAVLink 模式下的 ELRS）：姿态、位置、速度、模式、PID 参数，以及从地面切换模式。数据帧已与参考实现 pymavlink 核对。ESP32 没有空闲的 UART——那里用 Wi-Fi 仪表盘。以下是该阶段的原始记录。

**目标**：在真实配送所需的距离上实现飞机↔地面的通信，而不只是台架上的距离。**对现状的如实评估**：`WebDebugServer` 的 Wi-Fi 接入点如今已经能传送完整的聚合状态和控制命令，但普通 Wi-Fi AP 的距离只有几十米，用于桌面或机场调试足够，却不足以支持超出视距的自主航线。**技术上还需要**：一条距离更远的独立无线电通道（例如 LoRa 模块或专用的遥测数传电台），作为 `GET /api/status` 中已经定义的同一数据格式的传输载体——也就是替换或补充传输层，而不是重写遥测格式。

### 阶段 6 — 完整的地面控制 GUI [部分完成：QGroundControl / Mission Planner]

**状态**：得益于 MAVLink，标准地面站现在就能看到飞机（地图、返航点、仪表、以 ArduPlane 名称显示的模式）。为机队打造自己的地面站仍是目标。以下是该阶段的原始记录。

**目标**：一个带地图、实时遥测和机队管理功能的任务规划站，而不是只针对单架飞机的调试页面。**这与架构的契合方式**：`WebDebugServer.h` 如今已不是摆设，而是一个带聚合 JSON 状态和命令 API 的可用网页服务器（见 4.4 节的表格）；它就是出发点，而不是将来要扔掉的东西。下一步是显示当前位置的地图（阶段 3 之后）、航线的显示与上传（阶段 4 之后）、在远距离无线电通道上工作（阶段 5 之后），以及把界面从一架飞机扩展到多架。详见第 6 节。

### 阶段 7 — 载荷投放机构与配送所需的保护措施 [已在固件中完成，尚未试飞]

**状态**：载荷投放（AUX1 舵机，可放在任意拨杆上的 `PAYLOAD_DROP` 功能）、地理围栏（半径和高度上限 → RTH）、信号丢失时返航、“模型丢失”蜂鸣器。以下是该阶段的原始记录。

**目标**：把这个平台从“能自主飞行的飞机”变成“能自主配送的飞机”。**技术上还需要**：一个用于投放/放出货物机构的额外舵机，其控制原则与 `FlightOutputs.h` 中的其他输出相同；以及专门针对配送而非普通飞行的保护措施——地理围栏（限定飞行区域）和信号丢失时自动返回出发点（如今在空中丢失信号时，`FlightController` 会关闭电机并转入机翼水平的滑翔，这对手动操纵的滑翔机是合适的，但对自主配送而言，合乎逻辑的下一步是按 GPS 返回基地，而不是单纯滑翔）。

### 阶段 8 — 扩展到机队

**目标**：同时管理多架飞机——任务调度、运营面板、飞行历史。到了这个层面，项目就不再只是工程爱好者的原型，而成为一种运营工具，作为商业课题也值得关注：为多架飞机规划航线、任务队列、每架飞机的实时状态。从技术上讲，这是在阶段 3–6（GPS、遥测、GUI）之上的上层建筑——实质上还是同一套 `WebDebugServer` API，只是从一个遥测源扩展到多个遥测源。

## 6. GUI：从调试页面到地面站

本节的核心论点：GUI 不必从零开始构建——它已经部分存在并且能够工作。如今的 `WebDebugServer.h`：

- 提供飞机状态的统一聚合 JSON 快照（`GET /api/status`）——RC 通道、armed/failsafe 标志、每路输出的状态、每个传感器的状态（如实地用独立的 `attached` 和 `available` 标志表示）以及自动驾驶仪的状态；
- 实时接收控制命令（切换模式、修改 PID），无需重新烧录固件；
- 提供现成的 HTML 仪表盘，带有实时的通道条形图和控制按钮。

通往完整地面站的道路，是对已经在运行的协议做循序渐进的扩展，而不是更换架构：

1. 在仪表盘上加入地图和当前位置——这需要 GPS（阶段 3）作为同一个 JSON 状态里的又一个字段。
2. 加入航线的绘制与上传——这需要航路点模式（阶段 4），并仿照 `/api/setmode`/`/api/setpid` 扩展 POST API。
3. 把传输从 Wi-Fi AP 迁到远距离链路（阶段 5），保持同样的消息格式，这样现有前端就不必重写。
4. 把界面从一架飞机扩展到多个遥测源（阶段 8）。

换句话说，未来地面站中最容易被担心“是不是得从零写起”的部分——飞机状态的序列化和命令 API——已经实现，并且在开发板上经过了实测验证。

## 7. 如实说明的局限——哪些还不能用

为了让路线图不像营销文案，这里单独列出尚未完成或只完成了一部分的事项：

- 自动驾驶仪已在台架上、通过 387 个自动化测试和闭环仿真验证过，但从未在飞行中试过——到目前为止飞过的只有手动控制（在第一架原型机上）。仿真中的飞机模型是简化的，系数是初始值。
- 新传感器（LSM6DSV、ICM-45686、QMC6309、SPL06、BMP581）已用按数据手册编写的寄存器模拟器验证过，在硬件上还没有。
- STM32H743：整套固件在电脑上基于 STM32duino 的模拟替身运行；目前还没有实体开发板。
- 增稳所用的地平线是开机时飞机的姿态（IMU 每次启动都会校准），或者是按三个姿态做的安装校准。
- 舵机的物理连接无法由软件看出；能看到的只是脉冲确实从引脚输出（可在控制台中自检）。
- 普通 ESP32 38 针版的引脚分配是依据芯片文档选定的，没有在硬件上验证过。
- 许可证是 [OpenPlane License](LICENSE.md)：在 MIT 基础上要求必须署名作者，并禁止军事用途，以及未经当事人同意而故意危害人员和财产。由于这些禁止条款，它不被视为 OSI 意义上的“开源”许可证。

## 9. 如何联系与参与

目前项目唯一的官方渠道是 GitHub 仓库：
[github.com/damir-lebedev/OpenPlaneProject](https://github.com/damir-lebedev/OpenPlaneProject)
（分支 `main`）。目前不存在其他联系方式（邮箱、社交网络、法人实体），为避免误导，这里也有意没有列出。

- **Issues**——报告 bug，提出具体的技术修改建议，汇报你在自己那份原型上做飞行测试的结果。
- **Discussions**——讨论路线图、合作、在具体任务中的应用（配送、搜索与救援、农业），以及第 8 节中的许可和融资问题。
- **Pull requests**——通过 `Sensor` 接口添加新传感器，通过 `Config.h` 中的一个块添加新开发板，添加新的 `AutopilotMode`，改进网页仪表盘——架构的设计使这些都可以在不触动核心的前提下完成。
