# 블랙박스

> 🌐 이 문서는 [러시아어 원문](../../BLACKBOX.md)을 번역한 것입니다. 번역과 원문이 다를 경우 원문이 우선합니다. 펌웨어는 콘솔 메시지를 러시아어로 출력하므로 그대로 인용했습니다. 이 번역은 AI가 작성했으며 원어민의 검수를 거치지 않았습니다. 오류를 발견하면 [Damir Lebedev](https://github.com/damir-lebedev)에게 알려 주시거나 [이슈](https://github.com/damir-lebedev/OpenPlaneProject/issues)로 남겨 주세요.

펌웨어는 모든 비행을 스스로 보드 내장 플래시에 기록합니다. 센서, 스틱, 서보로 나가는 출력, 오토파일럿의 판단, 이벤트가 대상입니다. 비행이 끝나면 기록을 USB로 내려받아 CSV 표로 풀어 줍니다.

보드 두 종류에서 동작합니다.

| 보드 | 기록 위치 | 들어가는 양(약 20 KB/s 기준) |
|---|---|---|
| **ESP32-S3 N16R8** | 내장 플래시의 13.9 MB 파티션 | 약 **11분** |
| **STM32H743**(DevEBox: 주력, WeAct) | SD 카드의 파일, [아래](#sd-카드stm32h743) | 64 MB로 약 **55분**, 크기는 파일이 정합니다 |

다른 보드(ESP32-C3, 일반 ESP32)에는 저장 매체가 없어서 블랙박스가 꺼져 있고, 비행에 방해가 되지 않습니다.

## 언제 기록하나

| | 조건 |
|---|---|
| **시작** | ARM되어 있고 **동시에** 스로틀이 올라가 있을 때(스틱이나 ESC가 `THROTTLE_LOW_US`보다 높음). 그 **이전 10초**도 기록에 들어갑니다. ARM한 순간과 이륙 전 대기 시간입니다 |
| | 오류(패닉, 워치독, 전원 전압 강하)로 재부팅된 경우: 첫 제어 주기부터 최소 60초 동안 기록합니다. 공중에서 일어났다면 그 뒤에 무슨 일이 있었는지 볼 수 있습니다 |
| | 콘솔에서 수동으로(`k` → `r`): 테스트 벤치용 |
| **정지** | **DISARM 10초 뒤** |
| | ARM된 채로 모터가 멈춰 있고 비행기가 **30초 동안 움직이지 않을 때**: 착륙했거나 추락했는데 DISARM을 잊은 경우 |
| | 수동으로(`k` → `r`) |
| **정지하지 않음** | 통신 두절, failsafe, 공중에서 모터를 0으로 한 경우, 활공, 비행기가 아직 굴러가는 동안 DISARM 없이 착륙한 경우 |

"움직이지 않음"은 다음이 모두 동시에 성립한다는 뜻입니다. 모든 축의 회전이 5 °/s 미만, 가속도계가 1g ± 0.1을 가리킴, 기압계 기준으로 수직 속도가 거의 없음, GPS와 피토관(있다면) 기준으로 속도가 2 m/s 미만. 비행 중에 이렇게 조용한 상태가 30초 연속으로 이어지는 일은 없습니다.

## 무엇을 기록하나

| 레코드 | 주기 | 내용 |
|---|---|---|
| `IMU` | 제어 주기마다, 500 Hz | 자이로스코프(°/s), 가속도계(g), 제어 주기의 처리에 걸린 시간(µs) |
| `CTRL` | 100 Hz | 롤/피치/침로, 오토파일럿의 목표, 파일럿의 스틱, 최종 명령, **7개 출력 전부**(µs), 롤과 피치 PID의 성분(P, I, D), 파일럿과 오토파일럿의 스로틀, 플랩, 모드, 플래그(ARM, 통신, failsafe, 센서 정상 여부...), 켜진 기능 |
| `RC` | 50 Hz | 조종기의 10개 채널 전부, iBUS 프레임 카운터(정상과 손상) |
| `BARO` | 측정할 때마다(약 50 Hz) | 기압, 온도, 고도, 수직 속도, 고도 목표 |
| `MAG` | 최대 50 Hz | 3축 자기장, 방위 |
| `GPS` | 해(解)가 나올 때마다 | 좌표, 고도, 속도, 진로, 위성, 픽스, 정확도 |
| `AIR` | 최대 50 Hz | 피토관: 압력 차이, 지시 대기속도와 진대기속도, 밀도 |
| `NAV` | 10 Hz | 홈(거리, 방위각), 침로와 침로 목표, 내비게이션 속도, 침로의 출처, 손으로 던져 이륙과 소어링의 단계, 오토 트림 |
| `POWER` | 10 Hz | 배터리 전압과 전류 센서 출력(비행 컨트롤러 보드의 분압기, [FC_BOARD.md](FC_BOARD.md), B 블록) |
| `SYS` | 1 Hz | 제어 루프의 주파수와 최악의 주기, 남은 메모리, iBUS 카운터, IMU 온도, 블랙박스 큐, 유실된 레코드, 플래시에 쓴 가장 긴 시간, 남은 공간 |
| `EVENT` | 이벤트 발생 시 | ARM/DISARM, 이유가 붙은 ARM 거부, 모드 전환, 통신 두절/복구, 센서 고장/복귀, GPS 픽스, 홈 기록, 스위치 기능, 지오펜스, 실속 방지, 손으로 던져 이륙과 소어링의 단계 |

각 비행의 맨 앞에는 파라미터가 들어갑니다. 펌웨어(빌드 날짜), 시작과 직전 재부팅의 원인, 장착된 센서와 비행 전 점검 통과 여부, PID 계수(대시보드에서 바꾼 값 포함), 트림, `Config`의 중요한 값, 스위치 지정 내용입니다.

## 사용 방법

### 비행 전

할 일은 없습니다. 전원을 켜면 시리얼 모니터에 상태가 표시됩니다(콘솔은 러시아어로 출력합니다. 아래 줄은 "ARM과 스로틀 대기 중 | 앞쪽 삭제됨 12.9 MB(약 11분) / 전체 13.9 MB | 비행 1회"라는 뜻입니다):

```
BlackBox: ждёт ARM и газ | стёрто впереди 12.9 МБ (≈11 мин) из 13.9 МБ | полётов 1
```

"앞쪽 삭제됨"은 다음 비행에 들어갈 수 있는 양입니다. 전원을 켠 뒤 블랙박스는 몇 초 동안(긴 비행 뒤에는 최대 1분) 공간을 준비하며 오래된 기록을 지웁니다. 그동안 지상에서는 비행 루프가 ~0.15초씩 멈출 때가 있어 조종면이 늦게 움찔할 수 있지만 정상입니다. **공중에서는 플래시를 절대 지우지 않습니다.**

### 비행 후: 내려받기

1. USB를 **COM** 커넥터에 연결합니다. 시리얼 모니터는 닫으세요(포트를 잡고 있습니다).
2. 프로젝트 폴더에서 실행합니다.

   ```bash
   python tools/blackbox.py download          # 마지막 비행
   python tools/blackbox.py download --all    # 전부
   python tools/blackbox.py list              # 보드에 들어 있는 것
   ```

   `pyserial`이 필요합니다: `pip install pyserial`. 또는 이미 들어 있는 PlatformIO의 Python을 쓰세요: `%USERPROFILE%\.platformio\penv\Scripts\python tools\blackbox.py download`.

3. 비행은 `blackbox/` 폴더로 내려받아지고(약 200 KB/s: 10분 비행에 약 1분), 바로 옆의 같은 이름 폴더에 풀립니다.

내려받는 동안 비행 루프가 멈추므로, ARM하지 않은 상태에서만 동작합니다.

### 비행 폴더 안에 들어 있는 것

| 파일 | 설명 |
|---|---|
| `summary.txt` | 요약: 지속 시간, 주기, 각도·고도·속도·전압의 범위, 최악의 제어 주기, 유실된 레코드, 모든 이벤트 |
| `events.txt` | 비행의 파라미터와 시간순의 모든 이벤트 |
| `IMU.csv`, `CTRL.csv`, `RC.csv`, ... | 레코드 종류별로 표 하나씩 |

모든 표의 시간은 `time_s`로, 기록 시작(ARM과 스로틀)부터의 초입니다. 사전 기록 구간은 음수입니다. 값은 이미 단위로 환산되어 있습니다. 도, g, 미터, m/s, 펄스의 마이크로초입니다. `CTRL.csv`에는 모드가 이름으로 덧붙고(`mode_name`), 기능은 목록으로(`features_on`), 플래그는 0/1 열로 나뉘어 있습니다(`armed`, `rx_lost`, `fs_glide`, `imu_ok`...).

CSV는 Excel이나 LibreOffice에서 열 수 있지만, 시간에 따른 그래프를 그리려면 [PlotJuggler](https://github.com/facontidavide/PlotJuggler)가 더 편합니다: File → Load Data → CSV, 시간 열은 `time_s`입니다.

`.bbl` 파일은 플래시의 원본 이미지이며, 다시 풀 수 있습니다: `python tools/blackbox.py decode blackbox/flight_001_....bbl`.

### 콘솔: `k`

시리얼 모니터에서 `k` 키를 누르면 블랙박스 메뉴가 열립니다. 상태, 비행 목록, `r`로 기록 수동 시작/정지(테스트 벤치에서 확인용), `e`로 모든 비행 삭제(`y`로 확인, 약 40초)입니다.

## 플래시의 남은 공간

- 비행은 링 방식으로 기록됩니다. 공간이 모자라면 블랙박스는 지상에서, 앞쪽에 10 MB가 빌 때까지 **가장 오래된 비행을 통째로** 지웁니다(`BLACKBOX_MIN_FREE_BYTES`, 약 9분).
- **마지막으로 기록된 비행은 절대 지워지지 않습니다.** 다음 기록에 공간이 부족할 때 그 기록에 덮어써지는 경우만 예외입니다.
- 지워 둔 공간이 공중에서 바닥나면, 기록은 PSRAM의 큐에 이어서 쌓입니다(4 MB, 최근 약 3분의 데이터). 착륙해서 DISARM하면 블랙박스가 공간을 비우고 그것을 마저 기록합니다. 파티션 전체(약 11분)보다 긴 비행은 통째로 담기지 않아서, 앞부분은 남고 뒷부분은 사라집니다.
- 그러므로 **비행할 때마다 내려받으세요.** 특히 첫 비행 뒤에는 꼭 내려받으세요.

## 신뢰성

- 언제 전원이 끊겨도(추락, 배터리 이탈) 마지막 약 15 ms를 제외하고 모두 보존됩니다. 다 쓰이지 못한 레코드는 CRC로 걸러집니다. `summary.txt`에서는 이것이 "Недописанных записей (CRC)" 줄입니다(요약은 러시아어이며, "미완성 레코드 수(CRC)"라는 뜻입니다).
- 비행 번호, 링의 머리, 비행 목록은 섹터 자체에서 복원됩니다. 망가질 수 있는 별도의 "지도"가 없습니다.
- 내려받을 때 각 섹터와 비행 전체의 CRC-32를 검증합니다.

## 비행에 미치는 영향

- 비행 루프는 스냅샷을 PSRAM의 큐에 넣기만 하며, 몇 마이크로초면 됩니다. 플래시에는 코어 0의 별도 태스크가 한 번에 한 페이지(256바이트)씩 **제어 주기 직후에** 씁니다. 플래시에 쓰면 ESP32의 두 코어가 0.6–0.9 ms 멈추는데, 그 정지가 주기와 주기 사이의 틈에 들어가게 됩니다.
- 테스트 벤치에서의 측정(센서 없는 DevKit, 30–40초 기록 2회): 주기 간격은 2.00 ms이고, 간격의 99.2–99.7%가 1.9–2.1 ms 안에 들어오며, 가장 긴 것은 2.5 ms이고, 놓친 주기는 하나도 없었습니다. 주기의 작업량은 기록을 하지 않을 때와 같습니다. 주기가 눈에 띄게 흔들리는 것은 지상에서 ARM하지 않은 상태에서 블랙박스가 공간을 대조하고 지우는 동안뿐입니다(64 KB 블록 읽기는 약 3 ms 정지, 지우기는 약 0.15초).
- 센서가 있으면 한 주기는 약 0.7 ms이고, 페이지 쓰기는 남은 1.3 ms 안에 들어갑니다. 첫 비행 뒤 확인 방법: `summary.txt`의 "Такт IMU"와 "Цикл: худший такт" 줄을 보세요(러시아어이며 각각 "IMU 주기"와 "루프: 최악의 주기"라는 뜻입니다).

## SD 카드(STM32H743)

STM32H743에서는 블랙박스가 SD 카드(SDMMC1의 µSD 슬롯, 4비트, 24 MHz)에 기록합니다. 카드는 평범한 **FAT32**로 남습니다. 루트에 미리 만들어 둔 파일 `BLACKBOX.BIN`이 있고, 펌웨어는 그 안에 원시 블록을 쓰며 FAT 테이블이나 디렉터리는 절대 건드리지 않습니다. 그래서 비행 중에 전원이 끊겨도 망가질 것이 없고, 파일은 그대로 PC로 복사할 수 있습니다.

### 카드 준비(한 번만)

1. 카드를 **FAT32**로 포맷합니다(exFAT은 안 됩니다. Windows는 32 GB까지의 카드에 FAT32를 제안합니다).
2. 카드를 카드 리더에 꽂고 PC에서 실행합니다.

   ```bash
   python tools/blackbox.py sd-prepare E:              # 64 MB, E:는 카드의 드라이브
   python tools/blackbox.py sd-prepare E: --size 256   # 더 크게 하려면
   ```

   파일은 빈 카드에 연속된 한 덩어리로 만들어지고 `0xFF`로 채워집니다. 첫 섹터는 "링이 비어 있음"이라는 관리용 표시입니다. 파일이 연속되어 있지 않거나(카드가 비어 있지 않고 단편화가 심한 경우) 파일이 없으면, 전원을 켤 때 콘솔에 이유가 나오고 블랙박스는 꺼집니다.
3. 카드를 보드에 꽂습니다. 전원을 켜면 다음과 같이 표시됩니다(콘솔은 러시아어로 출력합니다. "SD 카드: 15204 MB, SDMMC 24 MHz, 4비트, 파일 BLACKBOX.BIN: 정상", 이어서 상태 줄, 마지막으로 "300 ms 만에 준비 완료"라는 뜻입니다).

   ```
   SD-карта: 15204 МБ, SDMMC 24 МГц, 4 бита; файл BLACKBOX.BIN: ок
   BlackBox: ждёт ARM и газ | стёрто впереди 0.7 МБ из 64.0 МБ | полётов 0
   BlackBox: готов за 300 мс
   ```

   "앞쪽 삭제됨"은 백그라운드에서 늘어납니다. 보드는 약 2.5 MB/s 속도로 공간을 대조합니다.

### 비행 기록 가져오기

- **보드를 거쳐 USB로**: ESP32와 같습니다. `python tools/blackbox.py download`(STM32의 콘솔은 USB CDC이고 내려받는 속도는 약 400 KB/s이며, 1 MB는 3초도 걸리지 않습니다). `list`, `--all`, `--flight N`도 똑같이 동작합니다.
- **카드를 빼서**: 카드의 `BLACKBOX.BIN` 파일을 그대로 CSV로 풀 수 있습니다.

  ```bash
  python tools/blackbox.py ring E:/BLACKBOX.BIN              # 모든 비행 -> blackbox/
  python tools/blackbox.py ring E:/BLACKBOX.BIN --list       # 목록만 출력
  ```

  파일은 섹터들의 링입니다. 도구가 섹터 번호를 보고 비행을 스스로 조립하며, 파일 끝을 넘어 처음으로 이어진 비행도 포함합니다.

| 삭제 | 64 KB는 13 ms, 64 MB 영역 전체는 20–28초 |
| 전원 켜기 | 링이 비어 있으면 0 ms(표시 덕분), 비행이 있으면 0.3초(약 530회 읽기로 하는 표본 대조), 64 MB 전체 대조라면 약 20초 걸림 |
| 20초 실시간 기록(500 Hz IMU) | 유실된 레코드 없음, 오류 0 |
| 기록 중의 비행 태스크 | 주기 편차 2 ms에 대해 **1 µs**(기록 옆에서 최고 우선순위의 모의 태스크를 돌린 경우) |

최악의 페이지 쓰기는 카드 내부의 "정리 작업" 때문입니다. RAM의 큐(384 KB ≈ 19초 분량의 데이터)가 이런 정지를 버텨 줍니다. 이 점에서 가장 차이가 크게 나는 것은 저렴한 카드입니다. 비행 전에 `test_blackbox_sd` 테스트로 카드를 확인해 두는 것이 좋습니다(최악의 쓰기가 250 ms 미만이어야 합니다. SD 규격의 한계입니다).

### ESP32의 플래시와 다른 점

- **쓰기 태스크**(`bbox`, 우선순위 2)는 카드에 접근하는 도중에 비행 태스크(5)에 의해 밀려납니다. 두 코어를 멈추는 ESP32처럼 "주기의 틈에서" 쓰는 것이 아닙니다. 전송에는 SDMMC의 하드웨어 흐름 제어를 사용합니다. 이것이 없으면 밀려날 때 FIFO가 넘쳤습니다(보드에서는 `HAL_SD_ERROR_RX_OVERRUN`이 뜨고 콘솔과 기록이 몇 초씩 멈췄습니다).
- **큐는 RAM에** 있으며, 4 MB PSRAM이 아니라 384 KB입니다(`BLACKBOX_RING_STM32_BYTES`).
- **전원을 켤 때의 대조는 표본 방식**입니다. 링의 진짜 섹터는 연속된 하나의 호를 이루므로, 헤더 약 500개를 읽고 호와 비행의 경계를 이분 탐색으로 좁힙니다. 결과는 전체 대조와 같습니다. 앞뒤가 맞지 않으면 전체 대조를 합니다.
- **"링이 비어 있음" 표시**는 파일의 첫 섹터에 둡니다. 전원을 켤 때마다 빈 영역을 몇 초씩 대조하지 않게 하려는 것입니다. 전체를 지웠을 때와 전체 대조에서 아무것도 찾지 못했을 때 붙고, 첫 기록 전에 떼어집니다.
- **카드 오류**(뽑힘, 버스 장애)는 1초에 한 번 이벤트 "носитель: ошибок записи …"로 로그에 남습니다(러시아어이며 "매체: 쓰기 오류 …"라는 뜻입니다). 유실된 페이지는 `0xFF` 구멍으로 남고, 섹터 해석은 거기서 멈춥니다(`tools/blackbox.py`와 같습니다). 나머지 섹터는 온전합니다.

### 플래시 위의 포맷

4 KB 섹터 = 16바이트 헤더(`magic "OPBB"`, 통번호 `seq`, 열었을 때의 `millis()`, 비행 번호, 포맷 버전, 검사 바이트) + 이어지는 레코드. 레코드는 섹터 경계를 넘지 않으며, 섹터의 꼬리는 `0xFF`입니다.

레코드: `[종류 u8][길이 u8][데이터][CRC-8]`이고, 데이터는 `t_us`(`micros()`)로 시작합니다. 비행의 첫 레코드는 `SCHEMA`이며, 텍스트 `"16 IMU t_us:I gx:h/10 ..."`가 들어 있습니다. 필드 이름, Python `struct`의 서식 문자, 나눗수입니다. 디코더는 필드 정보를 로그에서 가져오므로, 레코드에 새 필드를 추가하는 일은 `BlackBoxFormat.h`의 구조체와 스키마 문자열을 고치는 일이고(둘의 크기는 `static_assert`가 대조합니다), 디코더는 바꿀 필요가 없습니다.

### 내려받기 프로토콜

명령은 STX 바이트(`0x02`) 뒤에 오는 한 줄이며, 콘솔이 그것을 블랙박스에 넘깁니다.

```
PC:  \x02bb list\n
FC:  BB:STATE state=idle free_kb=... total_kb=... flights=... rate_bps=...
     BB:FLIGHT n=3 sectors=234 kb=936 seconds=41 start=1
     BB:END
PC:  \x02bb get 3 2000000\n
FC:  BB:SEND n=3 sectors=234 baud=2000000   (115200에서), 이어서 2 Mbaud로 전환
PC:  2 Mbaud로 전환하고 'G'를 보냄
FC:  234 프레임: A5 5A, u16 번호, 섹터 4096바이트, u32 CRC-32
     115200으로 복귀, BB:DONE n=3 crc=<모든 섹터의 CRC-32>
```

### 테스트

`pio test -e native -f native/test_blackbox_scan`: 무작위 이력(링 300개 × 탐색 단계 5회)에서 링의 표본 대조를 전체 대조와 비교하고, SD 영역에서의 비용을 측정합니다. `pio test -e native-stm32 -f native_stm32/test_blackbox_sd`와 `test_app_stm32_*`: FAT32, 영역, 카드 드라이버, 카드 위의 블랙박스, STM32 펌웨어 전체를 확인합니다. 보드에서는 `pio test -e stm32h743-devebox -f test_blackbox_sd`(실제 카드)를 실행합니다.

`pio test -e native -f native/test_blackbox`: 포맷, 파티션의 NOR 모의 장치 위의 링(섹터 단위 삭제, 쓰기는 비트를 내리기만 하며 비트를 올리면 오류로 간주), 재부팅, 전원 차단, 실제 `FlightController`/`Autopilot`으로 하는 비행 기록, 시작/정지, 이벤트, 공중에서의 플래시 넘침, 내려받기를 확인합니다. 디코더 검증용 비행 이미지는 다음 명령으로 만들 수 있습니다: `OPENPLANE_BLACKBOX_DUMP=/tmp/f.bbl pio test -e native -f native/test_blackbox`.
